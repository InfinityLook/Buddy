# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Buddy (formerly "SchoolBuddy") is a Czech-language, offline-first PWA companion app — for work, study and everyday life, not just school (see **Rebrand: SchoolBuddy → Buddy** below for what that repositioning actually touched). It is client-side first: "login" is still a local flag in `localStorage`, and **all** user data lives in the browser via Zustand-persisted state, which stays the source of truth. Since v1.7 there is one optional exception — gamification and two profile fields are additionally mirrored to Supabase (see **Cloud sync** below). Everything else — apps, all miniapp content, file blobs — is browser-only, and the app runs completely without the cloud. The pieces that structurally cannot work that way live in `api/`, deliberately as small and narrowly-scoped as each requirement demands: `buddy-chat.ts` (see **Buddy voice assistant**), because talking to a real AI needs a backend holding a secret API key, and `admin-ban.ts` (see **Admin panel**), because blocking someone's sign-in isn't something any client-side RLS policy can do. All UI copy and code comments are written in Czech; keep new strings/comments in Czech to stay consistent with the rest of the codebase.

## Commands

There is no lint setup (no ESLint/Prettier config). There is a standalone typecheck: `tsconfig.json` exists purely for `tsc --noEmit` (`noEmit`, strict, `noUnusedLocals`/`noUnusedParameters`); the actual transpile is still done by Vite/esbuild. Its `paths` mirror `resolve.alias` in `vite.config.ts` and `vitest.config.ts`'s own `resolve.alias` — all three must stay in sync (see **Path alias** below). Since this session, there's also a real test suite under `tests/` (Vitest for unit, `@playwright/test` for e2e) wired into GitHub Actions — see **Tests** below; `tests/components/` and `tests/security/` are the still-unbuilt tiers.

```bash
npm install         # install dependencies
npm run dev          # start Vite dev server on port 5173
npm run build         # production build (outputs to dist/)
npm run preview       # preview the production build locally
npm run typecheck     # tsc --noEmit
npm run test:unit     # vitest run — pure-logic unit tests, no browser needed
npm run test:unit:watch # vitest in watch mode, for local iteration
npm run test           # typecheck + test:unit — the fast gate to run before considering a change done
npm run test:e2e       # playwright test tests/e2e — needs npm run build first (preview server serves dist/)
```

Run `npm test` before considering a change done — it's fast (no browser) and is exactly what CI's first job runs. Run `npm run build && npm run test:e2e` before considering a *routing or auth-gate* change done — that's the tier that would catch it. `npm run test:security` (Playwright, against an isolated Supabase branch, not yet created — see **Tests** below) isn't wired up yet.

### Tests (`tests/`, `.github/workflows/ci.yml`)

Vitest for unit and (later) component tests, `@playwright/test` for e2e and security/RLS — chosen because Vitest shares Vite's own transform pipeline and `@/*` alias with zero extra config, and Playwright is already the tool this codebase's own manual verification has relied on all along (see the ad-hoc scripts referenced throughout this file's feature write-ups), just promoted to a committed, CI-runnable suite instead of one-off scratch scripts.

`tests/unit/` covers two things, both without rendering anything: pure functions (`xp.test.ts` against `gamificationUtils.ts`, `combat.test.ts` against `game/leveling.ts`, `finance.test.ts` against a handful of helpers `useFinance.ts` exports *only* for this — `dnesniMesic`/`minulyMesic`/`patriDoObdobi`/`rozdelPodleKategorie` were private before this test file needed them directly rather than through the whole hook), and the gamification **store's actions called directly** (`gamification.test.ts`, via `useGamificationStore.getState()`/`setState()` — Zustand stores work standalone, no React needed, so this still doesn't cross into the `tests/components/` tier). That last file resets the store's data fields in `beforeEach` with a plain merge, never `setState(x, true)` — `replace: true` would wipe the action methods too, since they live on the same state object as the data in a Zustand store created via `create()`. `vitest.config.ts` points `test.setupFiles` at `tests/setup.ts`, which pins `process.env.TZ = 'UTC'` (several tests here build dates from zone-less string literals, which parse as local time — pinning removes any dependency on which machine runs the suite) and a `matchMedia` shim jsdom doesn't provide, needed by the **later** `tests/components/` tier, not by anything here.

**`tests/e2e/` reuses this file's own manual-testing pattern — `ctx.route()` mocking Supabase, never a real backend — formalized into `tests/e2e/helpers.ts` instead of copy-pasted per script.** `mockSupabase()` is the generic table/RPC responder (GET with `eq`/`in`/`lt`/`gt` filters plus real `order`/`limit`, POST/PATCH/DELETE, named RPC handlers) that every ad-hoc script in this session's manual verification independently reimplemented; `vlozRelaci()` seeds a valid-looking session into `localStorage` before the app's first paint, same trick used throughout. `GET`'s `order`/`limit` started out ignored entirely — fine until Social's message pagination needed a test that could actually tell "returns the newest 50" apart from "returns everything and the client just slices," which an unordered, unlimited mock can't distinguish; it now really sorts and caps. `POST` fills in `null` for any column present on sibling rows but missing from the insert body, matching a real column default — without it, a test reading a freshly-inserted row's nullable column back (e.g. `messages.deleted_at`) sees `undefined` instead, which client code checking `=== null` treats differently than production ever would. `auth.spec.ts` is the first spec and deliberately the highest-leverage one: it asserts the `dovnitr` gate contract in `App.tsx` that every other route depends on (unauthenticated → redirected to `/`; authenticated → `/` itself redirects to `/hub`; authenticated-but-unpermissioned → `/admin` redirects to `/nastaveni`) — a regression here would break the entire app, not one feature, which is why it's the foundation rather than starting with a feature-specific spec. `playwright.config.ts` resolves its own `executablePath` conditionally (`/opt/pw-browsers/chromium` if that path exists, otherwise Playwright's own default resolution) so the same config runs unmodified in this sandbox and in a normal CI runner after `npx playwright install`.

**`tests/security/` cannot be meaningfully written against a mocked Supabase client, unlike `tests/e2e/`'s `ctx.route()` mocking.** A mock only proves the client *sent* the expected query — it can't prove a policy in Postgres actually *rejects* an unauthorized one, which is the entire point of an RLS test. These need to run against a real (isolated, non-production) Supabase branch with seeded accounts of each role, asserting actual `42501`/empty-result behavior from the live database — deliberately slower and more setup-heavy than the mocked e2e tier, worth the difference, and deliberately not started without an explicit go-ahead: `mcp__Supabase__create_branch` has a real cost that has to be confirmed before creating one, unlike everything else in this suite.

**CI (`.github/workflows/ci.yml`) is two independent jobs, not one, so a slow one never blocks a fast one.** `typecheck-and-unit` runs `npm test` on every push/PR with no setup beyond `npm ci`. `e2e` additionally installs a browser (`npx playwright install --with-deps chromium` — real CI runners don't have this sandbox's pre-installed one) and builds before testing, and uploads the HTML report as an artifact on failure. Both jobs hardcode `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` as plain workflow `env`, not GitHub Secrets — they're the "publishable" pair documented in `.env.example` as safe to ship inside the JS bundle anyone can already read, so a Secret would protect nothing that isn't already public. `OPENROUTER_API_KEY`/`SUPABASE_SERVICE_ROLE_KEY` are never in this file, on purpose — no test tier here exercises `api/buddy-chat.ts` or `api/admin-ban.ts` yet, and those two are genuinely sensitive (see **Buddy voice assistant** and **Admin panel**).

**Both jobs run on `node-version: 22`, not 20 — every CI run had been red since this workflow's very first commit, and this was the whole reason why.** `typecheck-and-unit` crashed before a single test ran: jsdom's own nested `undici` throws `webidl.util.markAsUncloneable is not a function` on Node 20, because `whatwg-url` (a jsdom dependency) needs `^22.14.0 || >=24.0.0` — `npm ci` even said so via an `EBADENGINE` warning nobody had looked at. `e2e` failed separately, for a different reason: `playwright.config.ts`'s `webServer` spawned `vite preview` without an explicit `--host`, and on this runner image `localhost` resolved to `::1` before `127.0.0.1` — the server came up fine on IPv6, but Playwright's own readiness probe only checked `http://127.0.0.1:4173`, so it waited the full 30 s and failed with a bare "Timed out" and no server output to explain why (`stdout`/`stderr` weren't piped, so there was nothing to look at even after the fact). The fix was three independent one-line changes, not one: bump both jobs to Node 22 (this sandbox had been validating every phase in this session on Node 22 the whole time — the mismatch was invisible locally because it only ever ran here), pin `vite preview --host 127.0.0.1` so both sides of the readiness check agree on the same address, and set `webServer.stdout`/`stderr` to `'pipe'` so the *next* CI-only failure — inevitably a different one — actually shows something to debug instead of a bare timeout.

## Architecture

### Rebrand: SchoolBuddy → Buddy (product repositioning)

**The app was renamed from "SchoolBuddy" to "Buddy," and repositioned from "for students" to "for everyone" — CLAUDE.md's own Social section had already flagged this as "a separate, explicitly deferred step" back when search-by-name shipped (see **Accounts & Social** below); this is that step.** The trigger was explicit: the product no longer wants to target only school-age students, and a name built around "school" fights that positioning every time a user sees it. The GitHub repo (`InfinityLook/Buddy`) and `README.md` had already anticipated the new name; the codebase itself hadn't caught up.

**The rebrand is deliberately a branding-and-copy change, not a data-migration.** Every string a user or admin actually reads — the PWA name/short_name/description (`vite.config.ts`'s manifest), `index.html`'s `<title>`/meta description/`apple-mobile-web-app-title`, the splash screen (`BootGate.tsx`), the login screen's brand name and footer copyright (`Login.tsx`), the Hub's header logo text (`Hub.tsx`), the "Verze aplikace" row and the profile badge (`ProfilModule.tsx`), the WebAuthn biometric prompt's relying-party name (`biometrics.ts`'s `rp: { name: ... }` — this is what the OS's actual Face ID/fingerprint dialog shows), the admin console's boot line (`KonzolePanel.tsx`), the Buddy voice assistant's own system prompt and OpenRouter `X-Title` header (`api/buddy-chat.ts`), the offline-ready console message (`registerSW.ts`), the default push-notification title (`push-sw.js`), backup download filenames and the "invalid backup file" error text (`backup.ts`/`fileBackup.ts`), and `package.json`'s `name` field — all became "Buddy." `tests/e2e/auth.spec.ts`'s assertion on the login screen's brand text was updated to match, since it's the one place a stale string would fail CI outright rather than just look wrong.

**Everything that is a stored identifier, not a display string, deliberately did NOT change — renaming those would silently corrupt or orphan every existing user's already-saved data, the exact mistake this file's own "Planer" rename (see below) was careful to avoid.** This includes: every Zustand `persist` store's `name` key (`schoolbuddy-*-storage`, all of them — `useAppStore`, `useAuthStore`, `useGamificationStore`, `useWalletStore`, `useRoleStore`, `useThemeStore`, `useProfileStore`, every miniapp's own store, every game-hub store), the two IndexedDB database names (`schoolbuddy-backups` in `backupHistory.ts`, `schoolbuddy-files` in `fileStorage.ts`), the backup file-format literal (`BACKUP_FORMAT = 'schoolbuddy-backup'` in `backup.ts`, matched exactly by `backupValidation.ts`'s `v.literal('schoolbuddy-backup')`), and — most critically of all — `secureStorage.ts`'s XOR obfuscation key, `ENCRYPTION_KEY = 'schoolbuddy_secure_key_2026'`. Changing that key would make every existing user's already-persisted localStorage data permanently unreadable on their next load; there is no migration path for an XOR key, only "old data becomes garbage." `vite.config.ts`'s two internal Vite plugin names (`schoolbuddy-version-meta`, `schoolbuddy-version-manifest`) were also left alone on purpose — they're plugin identifiers with zero user visibility, already named and documented as such elsewhere in this file, and renaming them would only churn a diff for no one to see.

**The "for everyone, not just students" repositioning touched copy, not features or scope.** The most visible school-specific framing was the profile card's unconditional "✦ AI Student" badge (`ProfilModule.tsx`, now "✦ Buddy Parťák") and the voice assistant's system prompt, which used to introduce Buddy as a companion "pro středoškolské a vysokoškolské studenty" (for high-school and university students) — now "parťák na produktivitu, studium i každodenní život, pro kohokoli, ne jen pro studenty." The default `USER_ROLE` also lost its backpack emoji (`🎒` → `👤`) and "Student" title (→ "Uživatel") — the only role of the four with school-flavored branding; VIP/Moderátor/Správce never had any. The `'Student'` display-name fallback used wherever a profile has no name yet (`social/api.ts`, `core/support/api.ts`, `biometrics.ts`, `useProfileData.ts`'s `DEFAULT_PROFILE.name`) became `'Uživatel'` for the same reason. **Individual miniapp names and content were deliberately left untouched** — "Maturitní centrum" (Czech high-school exam-prep) keeps its name; repositioning the app's own identity is a different, smaller decision than reworking or renaming a study-specific miniapp's own content, which nobody asked for here. Most other miniapps (Finance, Quick Notes, File Manager, Mind Map, Math Solver, Pomodoro, Form Check, Document Editor) were already general-purpose and needed no copy changes at all.

**Verified the same way every other change in this codebase's session history is**: `npm run typecheck && npm run test:unit` (57 unit tests, unaffected — none of them touch branding strings) and `npm run build`, then confirmed the built `dist/index.html`/`dist/manifest.webmanifest` actually carry "Buddy," then ran `tests/e2e/auth.spec.ts` against the real built app (4/4 passing) to confirm the auth-gate contract — the highest-leverage e2e spec in the suite — still holds with the renamed login screen.

### Routing & auth gate

`src/App.tsx` is the single `BrowserRouter` with eleven routes: `/` (Login), `/hub`, `/apps`, `/profil`, `/odmeny` (Rewards — level, streak and the full badge list; `src/pages/reward/`), `/nastaveni` (`src/pages/setting/`), `/obchod` (Shop; `src/pages/shop/`), `/social` (`src/social/`, `React.lazy` — see **Accounts & Social** below), `/hra` (the game hub; `src/game/`, also `React.lazy` — see **Game hub** below), `/podpora` (support tickets; `src/pages/support/`, see **Support systém** below) and `/admin` (Admin panel; `src/pages/admin/`, gated on more than sign-in — see **Admin panel** below). Every route except `/` redirects to `/` unless `useAuthStore().isAuthed` is true — there's no route-level guard component, the check is inlined per-`<Route>`. PWA update registration (`setupPWAUpdates`) is kicked off once from `App.tsx`'s `useEffect`.

### State: Zustand + encrypted localStorage

All persistent state uses Zustand's `persist` middleware backed by a **custom storage adapter**, `secureStorage` (`src/core/utils/secureStorage.ts`), which XORs values against a hardcoded key before base64-encoding them. This is obfuscation, not real encryption — don't treat it as a security boundary, and don't add secrets to persisted stores.

Stores live in `src/core/store/` (app-wide: `useAppStore`, `useAuthStore`, `useGamificationStore`) and additionally inside individual miniapp folders for feature-local state (e.g. `src/miniapps/pomodoro/usePomodoro.ts` has its own persisted store — see **Pomodoro** below for why the running timer itself lives there too, not just settings/stats). Follow this pattern: app-wide/cross-feature state goes in `core/store`, miniapp-local state stays colocated with the miniapp.

When persisted data can come from an external/untrusted source (e.g. JSON import), validate it with a `valibot` schema before committing to the store — see `core/utils/validation.ts` (`validateAppsData`), `gamificationValidation.ts`, `profileValidation.ts` and `backupValidation.ts`. The `persist` `migrate`/`merge` callbacks re-validate and fall back to defaults on corruption rather than trusting stored data blindly.

### Miniapps — the core feature unit

Each miniapp under `src/miniapps/<name>/` is self-contained: `<Name>.tsx` (component, named export), `use<Name>.ts` (hook holding logic, and its own Zustand store if it needs persistence), `types.ts`, `<Name>.css`. Look at `src/miniapps/pomodoro/` as the reference shape for a new miniapp.

Two places wire a miniapp into the app, and **both must be updated when adding one**:
1. `src/core/store/useAppStore.ts` — `DEFAULT_APPS` entry (id, title, category, icon, color) controls whether/how the app card shows up in `/apps`.
2. `src/features/miniapps/registry.ts` — `MINI_APP_REGISTRY` maps the same id to a `React.lazy()` import. Miniapps use named exports, so each lazy import is adapted with `.then((m) => ({ default: m.X }))` — `React.lazy` requires a default export.

`src/pages/app/AppModule.tsx` renders the grid of `AppCard`s from `useAppStore`, and when an app is selected, looks it up in `MINI_APP_REGISTRY` and renders it inside `<ErrorBoundary><Suspense>...</Suspense></ErrorBoundary>` (fallback UI at `src/components/ErrorBoundary.tsx`).

Other pages deep-link into a miniapp by setting `useAppStore().setActiveAppId(id)` before navigating to `/apps` (`AppModule` picks the id up from the store) — that's how the Hub's daily-challenge banner opens Planer (`id: 'study-planner'` — the id/hook/component names stayed put when the display title was renamed, see **Planer** below). To land on the grid pre-filtered to a category instead, navigate to `/apps?kategorie=<Category>`; `AppModule` seeds its `activeCategory` state from that param on mount only, so it stays a starting point the user can then change.

### Gamification

`useGamificationStore` (`src/core/store/useGamificationStore.ts`) tracks XP, level, streak days, badges and per-activity `counters` independently of any single miniapp. `recordActivity()` (called e.g. from `Hub.tsx` on mount) updates the streak and can unlock streak-based badges; `addXp()` recomputes level via `getLevelFromXp` and can unlock XP/level-based badges.

**Miniapps should award XP via `recordAction(kind, xp)`, not bare `addXp()`.** It bumps the matching counter, adds the XP and checks the count-based badge in `COUNT_BADGES` in one step, so the counter and the XP can never drift apart. `ActivityKind` lists the recognised kinds.

**A full audit of all 12 miniapps found exactly three that still called bare `addXp()` and so could never unlock a badge for their core action — Planer (task completion, called Study Planner at the time), Goal Tracker (goal completion) and Pomodoro (a finished work block).** All three were otherwise fully-featured; the gap was purely this one wiring. Fixed by adding matching `ActivityKind`s (`task`/`goal`/`pomodoro`), a `COUNT_BADGES` entry and a `DEFAULT_BADGES` entry each (`task_planner`/`goal_getter`/`focus_master`), and swapping their `addXp` call for `recordAction` — same XP amounts, no behaviour change beyond the new counter/badge. Pomodoro's own local `completedSessions` (shown in its UI, reset by its own "Vynulovat" button) stays a separate counter from the gamification store's `counters.pomodoro` — same relationship the game hub's per-character `leveling.ts` progress already has to the account-wide XP in this store, two different things measured for two different purposes. Exam Prep's two remaining bare-`addXp` call sites (`rateTopic`, `completeSimulation`) were deliberately left alone: its `exam_master` badge already has a working, hand-checked condition ("20 distinct topics rated") that doesn't fit `COUNT_BADGES`'s simple per-call-counter shape, so there was nothing broken to fix there.

Badge unlock conditions are hand-checked per action rather than declaratively — when adding a new badge, follow the existing pattern of checking-and-updating inline in the store action, using `core/utils/gamificationUtils.ts` for the level/streak math. New badges must be appended to `DEFAULT_BADGES`; the store's `merge` reconciles saved badges against that list on every load, so existing users pick up new badges without losing their unlock dates. Anything added to the persisted shape has to be **optional** in `core/utils/gamificationValidation.ts`, or older saved states fail validation and the user's progress is reset.

### PWA / offline

`vite-plugin-pwa` is configured in `vite.config.ts` (manifest, Workbox precache globs, dev-mode SW enabled), with `registerType: 'autoUpdate'` — so the generated `sw.js` calls `skipWaiting()`/`clientsClaim()` and `virtual:pwa-register` reloads the page once a new SW activates. `src/components/NetworkStatusBanner.tsx` + `core/hooks/useOnlineStatus.ts` show a fixed banner when `navigator.onLine` is false.

#### Versioning

`public/version.json` holds the single hand-maintained version number (`package.json`'s version is unrelated). At build time `vite.config.ts` reads it and derives a **build ID** (`<version>-<base36 timestamp>`) that changes on *every* build, so a deploy propagates to clients even when nobody bumped the version. Both values are injected in three places that must stay in sync:

- `__APP_VERSION__` / `__APP_BUILD_ID__` — `define`d into the bundle (typed in `src/vite-env.d.ts`, re-exported from `core/utils/registerSW.ts`).
- `<meta name="app-version">` / `<meta name="app-build-id">` in `index.html` — substituted by the `schoolbuddy-version-meta` plugin, so the *served HTML* carries the version of the build it came from.
- `dist/version.json` — rewritten by the `schoolbuddy-version-manifest` plugin in `closeBundle` (i.e. after Vite copies `public/`), gaining `buildId` and `buildTime`.

In dev the build ID is deliberately set equal to the plain version, and `public/version.json` has no `buildId`, so the comparison always matches and nothing reload-loops while you work.

#### Two update mechanisms

1. **Service worker (the graceful path).** `core/utils/registerSW.ts` (`setupPWAUpdates`, called once from `App.tsx`) is the *only* place that registers the SW — `main.tsx` must not register it too, or two Workbox instances race each other's reload. Beyond registering, it calls `registration.update()` every 5 minutes **and on every resume signal** (`visibilitychange`, `focus`, `online`, `pageshow` with `persisted`). Those resume triggers are the important part: a PWA launched from a phone's home screen is usually just woken from the background and never reloads on its own, which is why update-on-boot alone left users on a stale build for days. Before each `update()` it re-fetches `swUrl` with `cache: 'no-store'` to defeat the browser's 24h HTTP cache on `sw.js`, and nudges any SW stuck in `waiting` with a `SKIP_WAITING` message.
2. **`public/js/auto-update.js` (the watchdog).** A plain non-bundled IIFE loaded from `index.html` via an absolute `/js/...` path (a relative one would resolve to `/apps/js/...` and 404 on deep routes). It compares the `app-build-id` meta of the *currently served HTML* against a live no-store fetch of `/version.json` — comparing served-vs-server is what makes it able to detect "this client is stale", which the previous server-vs-server version could not do. On a mismatch it gives the SW `SW_GRACE_MS` to update gracefully, then falls back to unregistering the SW, deleting all Cache Storage, and `location.replace()`. A `sessionStorage` attempt counter caps this at `MAX_ATTEMPTS` reloads per version so a deploy race can't wedge the app in a reload loop, and it no-ops on localhost, offline, and while hidden. It is deliberately kept out of precache (`globIgnores`) so a stale copy can never be the thing that's broken.

`core/utils/registerSW.ts` also exports `hasNewerVersion()` / `applyUpdateNow()` / `checkForUpdates()`, used by the "Verze aplikace" row in `pages/profil/ProfilModule.tsx` as a manual escape hatch.

Practical consequences: keep `json` out of the Workbox `globPatterns` and keep the `NetworkOnly` runtime-caching route for `/version.json` — precaching it would freeze the version and silently disable both mechanisms. `vercel.json` sets `no-cache`/`no-store` headers on `sw.js`, `index.html`, `version.json`, `manifest.webmanifest` and `js/auto-update.js` while marking hashed `/assets/*` immutable; without those headers the CDN can serve a stale `sw.js` and no amount of client-side checking helps. Both `version.json` and `js/auto-update.js` must live in `public/` — anything outside it isn't copied to `dist/`.

### Cloud sync (Supabase, optional)

`src/core/supabase/` mirrors gamification (XP, level, streak, badges, activity counters) plus the profile's `name`/`motto` to a Supabase project. It is **strictly additive**: `client.ts` exports `isSupabaseConfigured`, and when `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` are missing the client is `null`, `startCloudSync()` returns immediately and the app behaves exactly as before. Never make a code path depend on the cloud being reachable — offline is the normal case, not the error case.

Identity comes from **anonymous auth** (`supabase.auth.signInAnonymously()`), started invisibly from `startCloudSync()` — the login screen is untouched. Each device therefore gets its own `auth.uid()`, and every table is locked to its owner by RLS. When a real login is built later, anonymous users can be upgraded to permanent accounts without losing rows.

The merge rule is **"higher wins"** (`merge.ts`, pure and unit-testable): max XP, max streak, max per-counter, union of badges keeping the earliest unlock date, level recomputed from the merged XP. This mirrors the decision already encoded in `BACKUP_STORES` — gamification is `restorable: false` because earned progress must never go backwards. Because of it, sync needs no clock comparison and is idempotent.

`cloudSync.ts` owns the wiring: an initial `syncNow()` (sign in → fetch → merge → write back locally → push), then debounced pushes on any store change, plus a resync on `visibilitychange`/`online` and a flush on `pagehide`. Sync status is exposed through `useCloudStatus` and shown as a row in `pages/profil`.

Schema lives in the `SChoolBuddy-System` Supabase project: `profiles` (one row per user, FK to `auth.users`), `user_badges`, `activity_counters`. Adding a synced field means touching the SQL, `CloudSnapshot` in `types.ts`, and `mergeSnapshots` together. Avatars are deliberately not synced — they are data URIs and belong in Storage, not a text column.

### Accounts & Social (`src/social/`)

**An account is required for the whole app**, not just Social. `App.tsx` gates every route on `useAccount().status === 'signed-in'` (`core/supabase/auth.ts` mirrors the real Supabase session: `off` / `loading` / `anonymous` / `signed-in`). Social therefore has **no gate of its own** — a second check would state the same rule twice and drift from the first one. This was a deliberate trade: the app is no longer usable without an account, so a new user with no signal cannot get in at all.

While `status === 'loading'` the app renders a placeholder rather than the login screen. Redirecting on `loading` flashes the login at users who do have a valid session and reads as an unexpected logout.

The one exception is `isSupabaseConfigured === false`. There accounts cannot exist at all, so the gate falls back to the local `isAuthed` flag — locking everyone out of a misconfigured build helps nobody and gives the user no way to fix it.

**Nothing creates anonymous sessions any more.** `ensureSession` returns the existing session or `null`; it never calls `signInAnonymously`. With login required, an anonymous account would be created on every start, immediately replaced by the real one, and leave an unreachable empty row behind. Sessions created by older versions are still honoured — `registerAccount` upgrades them via `supabase.auth.updateUser`, so those users keep the XP, streak and badges they earned before registering.

**The account rule is also enforced in the database.** `public.je_skutecny_ucet()` reads `is_anonymous` from the JWT and the INSERT policies on `messages`, `chats` and `friendships` require it. It still matters even though the client no longer creates anonymous sessions: RLS is what holds if someone talks to the API directly.

Signing out must call both `signOut()` and the local `logout()`. Clearing only the local flag leaves the Supabase session in the browser and the user is signed in again after a reload.

**Discovery is by friend code only** — there is deliberately no search by name. `profiles.friend_code` is 8 characters from an alphabet with no `I`, `O`, `0` or `1` so it survives being dictated over the phone. Lookup goes through `najdi_podle_kodu()`, a `SECURITY DEFINER` function returning one row and only name plus avatar; a normal RLS policy would have to permit reading every profile, which is the same as publishing a directory of children.

**Trigger functions must be `SECURITY DEFINER` if anything they call is revoked from `authenticated`.** The `profiles` insert trigger calls `vygeneruj_pratelsky_kod()`, which is deliberately not callable over `/rest/v1/rpc`. As `SECURITY INVOKER` the trigger ran with the caller's rights, hit that same revoke, and every profile upsert died with `permission denied for function vygeneruj_pratelsky_kod` — which killed cloud sync for XP and badges, far from anything that looked social. The app surfaced only "Synchronizace se nepovedla"; the reason is now shown under that row, because on a phone there is no console to check.

RLS helper functions take **one** argument and fill in `auth.uid()` themselves (`je_muj_pritel`, `je_blokovan_se_mnou`, `jsem_clenem`). The two-argument versions were callable over `/rest/v1/rpc` and let any signed-in user probe arbitrary pairs — enough to map the friendship graph. `jsem_clenem` must also stay `SECURITY DEFINER`: a policy on `chat_members` that queries `chat_members` recurses.

Blocking is symmetric and hides messages on read, so it covers group chats too. Deleting a message is soft (`deleted_at`), because a hard delete would remove the context an answer replies to.

**Reports reach a moderator.** `user_roles` is a separate table with a SELECT policy and *no write policy at all*, so a role can only be granted from the project dashboard — putting `role` on `profiles` would have let anyone set their own, because users may update their own profile row. `jsem_moderator()` gates report reading and resolving, and widens the `messages` and `profiles` SELECT policies just far enough to show the reported message and the two names involved. A moderator still cannot read ordinary private chats; that is asserted in the RLS tests.

`core/role/serverRole.ts` makes the server the authority for roles — the local store became the cache CLAUDE.md always said it would become. A network error deliberately leaves the stored role alone; dropping someone to `user` while offline would take away VIP they paid for.

**Unread messages are tracked app-wide** by `social/inbox.ts`, not only inside an open chat, so the Hub badge is right even when the user is elsewhere. It subscribes with no filter: Realtime applies the same RLS as a normal read, so only messages from the user's own chats arrive.

**A new message is also a third caller of `core/utils/notify.ts`, next to Pomodoro and Planer.** `inbox.ts` fires a system notification off the exact same condition it already used for the unread badge (not the user's own message, not the chat they currently have open) — the only extra step is resolving the sender's display name, since the realtime payload carries just the raw message row. `tag: social-${chatId}` means a second message from the same chat replaces the notification instead of piling up, the same collapsing behaviour Pomodoro's `tag: 'pomodoro'` already relies on. Permission is requested from `ChatView.tsx`'s send handler, synchronously before the first `await` — sending a message is this feature's clearest "I want to hear back" gesture, same reasoning as Pomodoro's Start button and Planer's `addTask`.

**Every realtime channel needs a unique name.** `supabase.channel(name)` returns the *existing* channel for a name already in use, and calling `.on()` on an already-subscribed channel throws — which blanked the entire app once the inbox and the Social screen both asked for `moje-zpravy`. `api.ts` appends a counter to every channel name.

**`INSERT ... RETURNING` also has to pass the SELECT policy.** `chats` is readable by `jsem_clenem(id)`, so `insert(...).select('id')` on a brand-new chat was rejected with `42501` — the creator only becomes a member on the *next* statement. Creating a chat therefore never worked at all. It now goes through `zaloz_chat(ucastnici, je_skupina, nazev)`, one `SECURITY DEFINER` call that creates the chat and every member together. That also removes an orphan-row hazard the three-statement version had: a failure after the first insert left a chat nobody was a member of, which no policy could then read or delete. Because it runs as the owner it re-checks the rules itself — real account, participants must be friends, nobody blocked — and returns the existing chat for a pair, so it is idempotent.

**Renaming a group and adding a member were already possible in the database before the client ever called them.** The RLS policies "přejmenovat skupinu smí její člen" (`UPDATE` on `chats`, gated by `jsem_clenem(id) AND is_group`) and "přidat člena smí zakladatel nebo člen" (`INSERT` on `chat_members`, gated by friendship + not-blocked) both predate `SpravaSkupinyDialog.tsx` — they just had no caller. `prejmenovatSkupinu`/`pridatDoSkupiny` in `api.ts` are therefore plain `.update()`/`.insert()` calls, no new migration. **Removing someone else, unlike those two, has no safe plain-RLS shape** — no policy can say "delete someone else's `chat_members` row" without that being exploitable by anyone. `odebrat_ze_skupiny(p_chat_id, p_cil)` is a new `SECURITY DEFINER` function, same shape as `admin_nastav_roli()`: it checks inside its own body that the caller is the group's `created_by` and that the target isn't the caller (self-removal stays "opustit chat", not this). `Chat.zakladatelId` (from `chats.created_by`, added to `nactiChaty()`'s select) is what the dialog uses to decide whether to even show the remove button — cosmetic only, the function re-checks regardless, same caveat as every other client-side role check in this file.

**`nactiZpravy()` used to return the 200 *oldest* messages of a chat, not the newest.** `.order('created_at', { ascending: true }).limit(200)` orders first, then cuts — for a chat past 200 messages that keeps the earliest ones and drops everything since, so reopening an active chat showed ancient history with no way to reach anything recent. It now orders descending, limits to `ZPRAV_NA_STRANKU` (50), and reverses the page for display; an optional `pred` cursor (the oldest loaded message's `createdAt`) pages further back, driving "Načíst starší zprávy" in `ChatView.tsx`. Sending or deleting a message no longer calls `nactiZpravy(chatId)` with no cursor to refresh the view — against the paged version that would silently drop any older history the user had already loaded, collapsing it back to just the newest 50. `poslatZpravu` now returns the inserted row (`insert(...).select().single()`, which passes the SELECT policy the same way `zaloz_chat`'s callers already worried about, because a message's own sender always satisfies "member of the chat, not blocked by the sender") so `ChatView.tsx` can append it directly; deleting patches the one row in place instead of refetching. `tests/e2e/helpers.ts`'s mock `GET` handler used to ignore `order`/`limit` entirely, which would have let the old, wrong pagination pass any test just as easily as the fix — it now actually sorts and slices, and its `POST` handler fills in `null` for columns present on sibling rows but absent from the insert body, matching what a real column default returns instead of leaving the key undefined.

**Leaving a chat didn't ask first, unlike removing someone else from a group.** It's an irreversible action for the person clicking it (their own chat history goes with it) sitting in the header next to lower-stakes buttons — one misclick away, the same class of risk `SpravaSkupinyDialog.tsx`'s member removal already guards with `window.confirm`. The leave button now asks too, phrased for group vs. 1:1.

**A group can now carry an emoji `icon`, because every group otherwise rendered the same bare "#" and was unreadable at a glance in a chat list with more than one.** Deliberately a fixed emoji picker (`IKONY_SKUPIN` in `types.ts`), not an uploaded photo — the app has no Storage wiring at all yet, and building upload plus the moderation question a freely-chosen image raises in a school-safety context is real, separate scope this wasn't worth pulling in for one cosmetic fix. The `chats.icon` column needed no new RLS: "přejmenovat skupinu smí její člen" is a row-level policy, not column-scoped, so whoever can rename a group could already have updated `icon` too.

**Reporting used to be reachable only from a chat message, never from a friend directly.** `nahlasit()` always accepted an optional `zpravaId` — nothing in the API required a message, only the UI never offered the path. Someone who'd only harassed via friend requests, or who a user just wanted to flag on sight, had no way in without manufacturing a conversation first. `PratelePanel.tsx` now opens the same `NahlasitDialog` with no `zpravaId`, next to the existing chat/block buttons on each friend row.

**Public search-by-name was proposed and declined once, on the grounds that the app was for students — that stance has since been reversed by a deliberate product repositioning (the app is moving from "for students" to for everyone; the rename itself, SchoolBuddy → Buddy, is a separate, explicitly deferred step) and search-by-name now ships.** The original objection still stands as *reasoning*, not as the current rule: a raw open directory (any signed-in account reading any other's name) is still the same problem it always was. What changed is that a school/class-scoped audience was the actual reason friend-code-only discovery made sense, and that audience assumption is gone. The fix follows this codebase's standing pattern for every other sensitive lookup (`najdi_podle_kodu()`, `admin_seznam_uctu()`) — a narrowly-scoped `SECURITY DEFINER` function, not a permissive RLS policy: `hledej_podle_jmena(dotaz text)` requires a 2+ character query (both in the SQL and again client-side in `hledejPodleJmena()`, so a single-character dotaz never round-trips at all), excludes the caller's own row, excludes anyone `je_blokovan_se_mnou()` in either direction (the same helper the friends/chat/block system already uses), and caps results at 20 — an unscoped `ilike '%...%'` over `profiles` with no cap would let one query enumerate a meaningful slice of the table. `PratelePanel.tsx`'s old "TVŮJ KÓD"/code-entry UI (paste-from-clipboard, share, auto-dash formatting) is gone from Social's screens, replaced by a "NAJÍT LIDI" search box; the underlying friend-code plumbing (`najdiPodleKodu`, `poslatZadost`, `formatujKod`/`ocistiKod`) is deliberately left untouched in `api.ts`, not deleted — it's reserved for a future secret-chat feature that will reuse the code as a shared secret rather than a discovery mechanism, so nothing about it needed to change to stop being Social's front door.

**The friend code's reserved future use — secret chat — now exists, restricted to VIP/moderator/admin, and it's genuinely separate infrastructure from `chats`/`messages`, not an extension of them.** `tajne_chaty`/`tajne_zpravy` are their own tables with their own RLS boundary, because the differences from a normal chat aren't cosmetic: only VIP/moderator/admin may participate (on *both* sides — a privileged account can't open one with a regular user), messages vanish 48 hours after being sent, and — the one place this deliberately isn't symmetric with normal moderation — a moderator gets no visibility into it at all; only `jsem_admin()` does, matching what was asked rather than reusing `jsem_moderator()`'s reports pipeline. Founding one goes through `zaloz_tajny_chat(cil)`, which requires the *invited* side to confirm via `potvrd_tajny_chat` before either party can write a message — mirroring `zaloz_chat()`'s orphan-row-avoidance shape, but with an acceptance step neither `zaloz_chat()` nor the old code-based friend request needed, since this one's whole premise is that both ends agreed to it. The target is still found by the friend code (`najdiPodleKodu`, unchanged) — this is the reuse the "reserved for a future secret-chat feature" comment above was written for, not name search, since a secret chat's whole point is that you need to already know who you're inviting.

Both role checks live behind `ma_pravo_na_tajny_chat(cil uuid)`, and it is **not** granted to `authenticated` — unlike the one-argument helpers this codebase already grants (`je_blokovan_se_mnou`), this one answers "does an arbitrary third party hold VIP/moderator/admin," which has nothing to do with the caller's own relationships and would leak role status for anyone if it were RPC-callable. It's only ever invoked from inside other `SECURITY DEFINER` functions, which run as the owner regardless of who called them. **This exact mistake shipped once during this feature and was caught by `get_advisors`, not written correctly the first time**: Postgres grants `EXECUTE` to `PUBLIC` on a function by default, and forgetting the explicit `revoke` meant `ma_pravo_na_tajny_chat` really was callable over `/rest/v1/rpc/ma_pravo_na_tajny_chat` by anyone, signed in or not, for the short window before the follow-up migration revoked it — fixed and re-verified against real production data via role/JWT impersonation before shipping (both privileged-pair founding and rejected-target founding, founder-can't-self-confirm, non-participant and demoted-mid-conversation sends all raising the right error, and the RLS boundary actually hiding rows from a non-participant).

Sending a message goes through `posli_tajnou_zpravu(chat_id, text)` rather than a plain insert (unlike `support_zpravy`'s "an ordinary reply needs no wrapping RPC" — the difference is this insert has to re-check the sender still holds VIP/moderator/admin *at send time*, not just when the chat was founded, and that check can only happen inside a function that already runs as the owner). Expiry is enforced twice, the same "belt and suspenders" shape as everywhere else expiry appears in this codebase: the SELECT policy hides any row past `expiruje_at` immediately regardless of whether it's been physically deleted yet, and `smaz_expirovane_tajne_zpravy()` (no pg_cron — this project doesn't use it anywhere — just a client-called cleanup on opening the panel or sending a message) actually removes the row later. Nothing breaks if the cleanup call is skipped or fails; the policy alone already makes an expired message unreadable.

On the client, `social.secretChat` (`core/role/`) is a UI-only convenience gating the new "Tajný chat" tab — granted to `VIP_ROLE`/`MODERATOR_ROLE`/`ADMIN_ROLE`, nobody else — same caveat as every permission in that folder: the real boundary is the database, this only decides whether the tab renders. `useTajnyChat.ts` is deliberately its own hook, not folded into `useSocial.ts`, because most signed-in accounts don't have the permission at all and shouldn't pay for a query that will always come back empty for them. `TajnyChatPanel.tsx`/`TajnyChatView.tsx` are visibly thinner than `PratelePanel.tsx`/`ChatView.tsx` — no message delete, no report, no presence/typing, no leave — none of that was asked for, and the vanishing-by-design nature of the content makes manual deletion mostly redundant with what time already does. A rejected invite used to have no retry path — `zaloz_tajny_chat` was idempotent like `zaloz_chat()`, so calling it again after a decline just returned the same `zamitnuto` row forever — fixed in a later pass, see below.

**Two gaps in the first pass were closed in a follow-up hardening migration, both flagged by asking rather than assumed complete.** First, blocking was only checked at `zaloz_tajny_chat` founding time — nothing stopped either side from continuing to message, or from confirming, a relationship blocked *after* the invite existed. `potvrd_tajny_chat` now refuses to activate a chat if the confirming party is blocked with the founder, and `posli_tajnou_zpravu` re-checks `je_blokovan_se_mnou()` against the specific other participant on every send — deliberately only new activity, not retroactive: blocking stops what happens next, it doesn't erase what was already sent, same distinction `smazatZpravu`'s soft-delete already draws elsewhere in Social. Second, `audit_log` didn't know Secret Chat existed at all — admin, the one role with any oversight here, had no trail of who founded or confirmed a chat with whom, without reading a single message. `zaloz_tajny_chat`/`potvrd_tajny_chat` now call the existing `zapis_audit_log()` (same helper `admin_nastav_roli()`/`zabanuj_ze_social()` already use, no new logging mechanism) — founding logs once only on an actual new row, never on the idempotent "already exists" return, so a repeated call can't pad the log with duplicates; confirming logs as `potvrdit_tajny_chat` or `zamitnout_tajny_chat` depending on the outcome, targeting the founder's id since they're always the other side of a confirmation. `nacti_audit_log()`'s `admin_id` column is really just "the actor," already generic enough to hold a VIP's or moderator's id with no schema change — `AuditLogPanel.tsx` only needed the three new action codes added to its `POPIS_AKCE` label map. Both additions verified against real production data via role/JWT impersonation the same way the original feature was: blocked-before-confirm rejected, blocked-mid-conversation send rejected, both audit rows written with the right actor/target/action, all test rows cleaned up after.

**Secret Chat messages are now genuinely end-to-end encrypted, and the vanish timer is configurable per chat instead of a fixed 48 h — both explicitly asked for, because "tajný" had, until now, only meant access-controlled, not actually unreadable to the server.** `tajne_zpravy.text` still exists as a column, but from this migration on it holds base64 AES-GCM ciphertext, not Czech text — the server (and the database `SELECT` policy that lets `jsem_admin()` read the table for oversight, see above) never sees plaintext, only that a message of some size passed between two people at some time. This is a deliberate consequence of the earlier design decision that only `jsem_admin()` gets any visibility into Secret Chat at all: admin oversight was always going to be metadata-only in spirit (who, when, via `audit_log`), and E2E just makes that true of message content too, not only of the moderator exclusion.

The crypto is ECDH (P-256) + AES-GCM, plain Web Crypto (`crypto.subtle`), no library — `tajnyChatCrypto.ts` is pure crypto with no Supabase import at all, keeping faith with "`api.ts` is the only place Social talks to Supabase" by simply never needing to: it hands api.ts already-encrypted `{cifra, iv}` to send and already-imported `CryptoKey`s to decrypt with, api.ts just moves bytes. Each device generates its own ECDH key pair once (`zajistiKlicovyPar()`), stores it in its own IndexedDB (`CryptoKey` is structured-cloneable, so it's saved the same direct way `fileStorage.ts` already saves file blobs — no serialization, no `secureStorage` XOR obfuscation involved, because obfuscating an already-non-extractable-in-practice key would add nothing), and uploads only the public half (`tajne_klice`, one row per user) — the private half never leaves the device. Neither side's AES key is ever transmitted or even computable by the server: each device derives the *same* symmetric key independently from its own private key plus the other side's public key, an inherent property of ECDH, not a protocol the server participates in. `tajne_klice`'s RLS follows this file's usual restraint even though public keys are, by definition, not secret: `SELECT` is scoped to your own key or a key belonging to someone you already share (or are founding) a Secret Chat with, not an open directory — the same reluctance to publish an unscoped list of anything about a user that governs `najdi_podle_kodu()`/`hledej_podle_jmena()` above. Uploading your own key needed no `SECURITY DEFINER` wrapper, just a plain `user_id = auth.uid()` `INSERT`/`UPDATE` policy — the same "can't claim someone else wrote it" shape as `client_errors`/`oznameni`, since there's no privilege question in writing your own public key.

**A lost device is a lost key, and that's an accepted trade, not a gap that needs solving** — `useTajnyChat.ts` uploads the device's key the moment Social loads with the permission (not only when a chat is opened, so the key is already there by the time anyone tries to reach that person), but nothing links keys across devices or backs one up. Clearing site data, reinstalling, or switching phones means a fresh key pair and permanently losing the ability to decrypt anything encrypted under the old one — for a *normal* chat this would be unacceptable data loss; for Secret Chat, where nothing outlives `expirace_sekund` anyway (12 h at the outside), the exposure window this could ever matter in is already bounded by the feature's own premise. `TajnyChatView.tsx` treats "other side has no key yet" as a real, expected, non-error state (`klicStav: 'chyba'`, input disabled, a plain explanation) rather than a crash — it happens routinely for the ordinary reason that the other participant simply hasn't opened Social since gaining the permission.

**The vanish timer moved from a hardcoded interval to `tajne_chaty.expirace_sekund`, a value either participant can change, applying only to messages sent from that point on** — same non-retroactive posture as the blocking enforcement above, and the same reasoning: a timer that could reach backward and change what an already-sent message's fate is would be a stranger, less predictable feature than one that just governs what happens next. The allowed set (10 s/30 s/1 min/5/10/15/30 min/1/4/8/12 h) is a database `CHECK` constraint, not just a client-side `<select>` — `nastav_expiraci_tajneho_chatu(chat_id, sekund)` re-validates it server-side too, so a value outside the list can't reach the column via any path. Changing it goes through this one `SECURITY DEFINER` function rather than a plain `UPDATE` policy on `tajne_chaty`, even though "change your own chat's timer" sounds as harmless as `chats.icon`'s plain-RLS shape elsewhere in this file — the difference is that `tajne_chaty` has no `UPDATE` policy *at all* by design (every state transition, `stav` included, is meant to go exclusively through `zaloz_tajny_chat`/`potvrd_tajny_chat`), and Postgres RLS has no per-column granularity: a permissive `UPDATE` policy scoped to "you're a participant" would just as easily let a client `PATCH` `stav` directly, silently reintroducing the exact "founder confirms their own invite" hole `potvrd_tajny_chat` exists to close. `CASOVACE_TAJNEHO_CHATU` (`types.ts`) is the one shared source for the preset list — the `<select>` in `TajnyChatView.tsx`'s header and the constraint's allowed values must never drift apart, so both are meant to be edited together.

**Verifying the crypto needed a real browser, not SQL impersonation** — cryptographic correctness (does device B actually recover what device A encrypted, using a key it derived independently) isn't something Postgres role-switching can prove, unlike everything else about this feature. A temporary two-`BrowserContext` Playwright spec (deleted after, per this file's own standing practice) ran two genuinely separate Chromium profiles, each generating a real ECDH key pair via its own `crypto.subtle`, sharing one in-memory mocked "backend" object between them — proving an actual round trip: A's plaintext survives encryption, transport as opaque ciphertext (asserted to not contain the original text), and independent decryption on B using a key B never received over the wire. A second spec asserted the deliberately-not-solved case above renders as a clear, non-crashing state rather than silently doing nothing.

**A profile dialog (`VerejnyProfilDialog.tsx`) now shows anyone's level/XP/streak/role from three entry points — friends, a 1:1 chat header, and search results — through one shared component rather than three bespoke views.** The data (avatar/name Social already had; level, XP, streak and role tag are new) goes through `precti_verejny_profil(cil)`, a `SECURITY DEFINER` function, not a wider `profiles` `SELECT` policy — `profiles` already has a row-level policy covering friends and chat co-members ("číst svůj profil, profily přátel a spoluúčastníků chat"), but that policy has no case for someone found via `hledej_podle_jmena()` who isn't a friend yet, and building two different code paths (plain `SELECT` for two entry points, a function for the third) so the same dialog behaves differently depending on where it was opened from wasn't worth it for four columns that aren't especially sensitive to begin with — one function, one behavior, everywhere.

**This function repeated, and this time caught before shipping, the exact mistake `ma_pravo_na_tajny_chat` made earlier in this session.** It only guarded against blocked targets via `je_blokovan_se_mnou(cil)` — which, evaluated with `auth.uid()` `NULL` (an unauthenticated caller), simply finds no matching block and returns `false`, so `not je_blokovan_se_mnou(cil)` is `true` regardless of whether anyone is signed in. Sibling functions in this codebase (`hledej_podle_jmena`, `najdi_podle_kodu`) happen to be safe anyway because they separately compare `p.id <> auth.uid()`, which is `NULL` (falsy) for an anonymous caller and quietly excludes every row — this function had no such incidental protection. Caught this time by testing the anonymous case directly (`set local role anon`) before calling anything else finished, not by `get_advisors` after the fact — an explicit `auth.uid() is not null` guard was added to the query itself, verified to return zero rows anonymously, full data once actually signed in, and nothing at all for a blocked target.

Actions live in the dialog itself, not only on the row that opened it, because search results have no row-level buttons to fall back on: `pritel`/`zadostOdeslana`/`jeZablokovany` are derived from the already-loaded `SocialStav` (no extra fetch) to decide whether to offer "Napsat" (existing friend, opens the real chat via `otevritChatSPritelem`), "Přidat" (not yet connected), or "Žádost odeslána" (already sent, disabled) — Nahlásit and (un)block are always available except against your own profile. The 1:1 chat header becomes a `<button>` wrapping the same title markup a `<span>` used to hold (reset via `.social-chat-title--klikatelny`, `all`-equivalent CSS, not a new visual style) — a *group* header stays a plain `<span>`, on purpose: there's no single "them" to open a profile for, and building a member-picker for that case wasn't asked for. Every row that opens a profile (friends, both directions of pending requests, search results) wraps its avatar+name in a `<button>` **sibling** to the row's existing action buttons, not their parent — a `<button>` inside a `<button>` is invalid HTML, the same rule `PostavaKarta` in the game hub already follows for its own delete button.

**Three small, deliberately scoped gaps flagged right after Secret Chat and the profile dialog shipped were closed in one pass — a retry path, a notification, and one more profile entry point.** None of them were new features on their own; each just brought something already built into line with a pattern the rest of the app already uses.

A rejected Secret Chat invite was a dead end — `zaloz_tajny_chat`'s idempotent "return the existing row" behavior meant a decline was permanent, because the unique index on the pair meant there was only ever one row to return. It now special-cases that one state: finding an existing row with `stav = 'zamitnuto'` resets it to `cekajici` with `zalozil` set to *whoever just called it* (not necessarily the original founder — either side can re-invite, including the one who declined the first time) and `potvrzeno_at` cleared, logging to `audit_log` the same way a genuinely new invite does. This is safe specifically *because* a rejected chat never reached `aktivni` — `posli_tajnou_zpravu` requires that state, so a declined invite can never have any messages attached to revive along with it. Verified both directions on real data (original founder re-inviting, and the declining party inviting back — the harder case, since it swaps who `zalozil` is and who `potvrd_tajny_chat` will require to confirm next). `TajnyChatPanel.tsx` gained a "ZAMÍTNUTÉ" section so a decline is visible instead of the chat silently vanishing from every list — the hint text points back at the same code-entry form above it, since that's literally how the retry works, no separate "re-invite" button needed.

New Secret Chat messages didn't notify at all, unlike regular chat's `inbox.ts`. The fix (`useTajnyChat.ts`, a new `sledovatVsechnyTajneZpravy` in `api.ts` mirroring `sledovatVsechnyZpravy`) deliberately shows a *generic* body ("Nová zpráva v tajném chatu"), never the decrypted text — not merely because decryption isn't available in this global-subscription context (the shared AES key only gets derived inside an open `TajnyChatView.tsx`), but because an OS notification tray isn't a secure surface, and putting plaintext there would undercut the E2E design this feature was built around. The sender's name is shown, though — that's not secret, it's visible everywhere else in Social already. Self-exclusion and "don't notify about the chat currently open" both mirror `inbox.ts`'s `otevrenyChat` mechanism exactly, via a new parallel `otevrenyTajnyChatId`/`nastavOtevrenyTajnyChat` module-level pair kept in `useTajnyChat.ts` rather than folded into `inbox.ts` itself — same reasoning as everywhere else Secret Chat stays its own module: most accounts never have the permission and shouldn't carry its state. This one couldn't be e2e-verified like the rest of this session's Supabase-touching work: `tests/e2e/helpers.ts`'s `mockSupabase()` intercepts HTTP via `ctx.route()`, not WebSocket, so a `postgres_changes` Realtime event has no way to fire inside that mock at all — every other Realtime-dependent check in this codebase's e2e suite works around that the same way (a `page.reload()` re-fetching over HTTP, never an actual live event), and this is the first feature where nothing consumes the *content* of a live event, so there's no equivalent workaround. Verified by type-safety and by construction: the code is the same shape as `inbox.ts`'s already-shipped, already-relied-upon version of the identical check.

The profile dialog could already open from a chat header, but only for a 1:1 — a *group* header stayed a plain, non-clickable `<span>` on purpose, since there's no single "them." Its member list (`SpravaSkupinyDialog.tsx`) is the obvious place group members actually live, so each member row's avatar+name got the same `.social-row-otevrit` sibling-button treatment `PratelePanel.tsx` already uses, threaded through as one more `onOtevritProfil` prop from `ChatView.tsx`. No new capability — it's the same dialog, the same `precti_verejny_profil`, just reachable from one more list of people this codebase already had one.

**`tests/e2e/helpers.ts`'s mock `POST` handler didn't understand `.upsert()`, and that silently broke a test that had nothing to do with upserts.** `cloudSync.ts` upserts the profile row on every app boot (`on_conflict=id`); the mock's old "always push a new row" behavior turned that into a *second* row with the same id, and a subsequent `.maybeSingle()` read (`nactiMujProfil()`) got back more than one match — which reads as an error and made the own-profile card show placeholder dots instead of the real friend code, in a test that was only trying to verify the share button's text. `POST` now honors `on_conflict`: a matching existing row (by that column) gets `Object.assign`-updated in place instead of a duplicate insert.

**Supabase errors are plain objects, not `Error`s.** A helper testing `err instanceof Error` therefore never matched, and every database failure reached the user as "Nepovedlo se to." — including the ones whose `message` said exactly what was wrong. On a phone there is no console, so that hid a 403 for hours. `chyba()` in `api.ts` reads `message`/`hint`/`code` off the object.

**Anything the UI must notice on its own needs to be in the `supabase_realtime` publication.** Only `messages` was, so a friend request sat invisible on the other device until Social was reopened, and it looked like sending had failed. `friendships` is in it too now. Realtime applies the same RLS as a normal read, so an unfiltered subscription still only delivers the user's own rows.

**Report the real reason, not the most likely one.** `najdiPodleKodu` used to return `null` for "nobody has that code", "that's your own code" and "the request failed" alike, and the UI always said the first. Entering your own code — the obvious thing to try with two devices — produced a flat lie. It returns a `NalezVysledek` discriminated union instead, and the panel checks the own-code case against `stav.profil.friendCode` before asking the server, because `najdi_podle_kodu` deliberately skips `auth.uid()` and cannot report it.

`src/social/api.ts` is the only place that talks to Supabase; components receive finished shapes. Realtime subscriptions return an unsubscribe function — `ChatView` must call it, or every visit leaves another open channel.

**Social carries a real Three.js scene as an ambient backdrop** (`social/scene/useAmbientScene.ts`) — a handful of soft glowing spheres drifting slowly behind the glass cards, matching the Hub orb's calm/subtle motion level but rendered in true 3D per an explicit choice (a CSS pseudo-3D approach was offered and declined). The scene lives entirely outside React — owns its own renderer, camera and render loop, cleans up every geometry/material/renderer on unmount, one `<canvas>` no matter how many times the user leaves and returns (verified by round-tripping in and out of `/social` three times) — the same ownership shape as Form Check's `usePoseEngine.ts` (camera/ML pipeline) and, formerly, the Game hub's now-deleted city scene: React only ever gets told what to render, never owns the loop itself. Because of that dependency, `SocialModule` is lazy-loaded in `App.tsx` — Social opens far more often than the game hub ever did, so it would have been the worse place to eat the Three.js weight unconditionally. The scene is decorative only (no raycasting, no controls) and stays `pointer-events: none`; it fades out via CSS opacity while a chat is open rather than unmounting, because unmounting the container would orphan the live WebGL canvas with nowhere to reattach when the chat closes.

**A real "Social loads slowly" complaint traced back to `useAmbientScene.ts`'s `import * as THREE from 'three'` being a static, top-level import — not a network-latency problem at all.** `SocialModule` is itself `React.lazy`-loaded, and its whole static-import graph (including anything `useAmbientScene.ts` pulls in) has to finish downloading *and executing* before React is allowed to render any of it — profile, tabs, friend list, all of it, gated on a purely decorative background finishing first. `three`'s minified/gzipped weight (over 100 KB gzip on its own) made that wait genuinely noticeable, confirmed by artificially delaying the `three.module` chunk's network response in a temporary Playwright spec (deleted after passing): the old code left the profile heading still unrendered past 3 seconds, the fixed version painted it in ~270 ms regardless. The fix moved the import inside `useAmbientScene`'s own effect (`await import('three')` instead of a top-level import, with `import type * as THREE from 'three'` kept at the top for the type-only uses in cleanup — erased at build time, zero runtime cost) — the actual profile/friends/chat UI no longer waits on Three.js at all; the ambient scene just fades in a beat later once its own chunk resolves, exactly the deferred-loading shape `Explorace3D.tsx` already uses for the game hub's own Three.js weight (see **3D exploration** below). **This trade isn't free**: crossing a dynamic `import()` boundary makes Rollup's tree-shaking measurably weaker for the shared `three.module` vendor chunk (both this hook and the game hub's `usePlayerWorld.ts` already use the same tree-shaking-defeating `import * as THREE` namespace form, so the chunk was never small to begin with) — the shared chunk grew by roughly 60 KB gzip, and since `vite.config.ts`'s PWA `globPatterns` precaches every built `.js` file regardless of whether it's reached by a static or dynamic import, that extra weight is paid once by every install, not saved by anyone who never opens `/social` or `/hra`. Accepted deliberately: a one-time, amortized install-time cost is a better trade than blocking every single visit to Social's own initial render on a background nobody is looking at yet.

**Avatars get a colour from the user's id, not a fixed gradient.** A flat cyan→violet circle for every single person made a friends list unreadable at a glance — nothing distinguished one row from the next except the name text. `avatarColor.ts` hashes the id to a hue deterministically (same id → same colour on every device, nothing stored), and `SocialAvatar.tsx` draws it as a rotating conic-gradient ring around the initial, using the same mask-based hole-punch as the Hub orb's ring (see the Hub section above) rather than the old padding-box trick, which breaks over a non-opaque background.

**Presence (who's in a chat right now, who's typing) is deliberately scoped per chat, not a global "who's online" list.** A shared app-wide presence channel would let anyone who once saw your id — even a friend request you rejected — keep watching whether you're online forever. `sledovatPritomnost(chatId, mujId, …)` in `api.ts` instead opens one Realtime channel per open chat, combining Presence (`track()`/`presenceState()`) and a `broadcast` typing event on the same channel — both only ever reach people who already share that specific chat, the same boundary `sledovatChat`'s `postgres_changes` filter already uses. The "online" dot on a 1:1 chat and the "N tu teď" count on a group therefore mean "has this chat open right now," not "has the app open" — a narrower, honestly-labelled claim that happens to be exactly what the presence channel can actually prove. Typing is throttled client-side (one broadcast per 2 s while text keeps changing) and self-clears after 3 s of silence on the receiving end — no separate "stopped typing" event needed, same "let it time out" reasoning as Pomodoro's completion-notification fallback.

**Social Fáze 1 (read receipts, reactions, reply, mute) added four independent messaging-app basics in one pass, all built on existing infrastructure — no new privileged function, only plain self-row/membership RLS.** Chosen deliberately as the next four features because none of them needed anything this app didn't already have: `chat_members` already carried a `last_read_at` per member, `messages` already had the shape a `reply_to_id` self-reference slots into, and reactions are the one genuinely new table, but its RLS mirrors `messages`' own INSERT check almost verbatim.

**"Přečteno" (read receipts) needed no new column at all — `chat_members.last_read_at` already existed per member, just never read for anyone but yourself.** `nactiChaty()` only ever selected the caller's own row (`eq('user_id', ja)`); the `chat_members` SELECT policy (`jsem_clenem(chat_id)`) already lets any member read *every* member's row of a chat, own or not, so exposing it for read receipts was a client-side change only — `nactiPrectenost(chatId)` fetches the whole chat's member rows, `sledovatPrectenost` subscribes to `UPDATE` on `chat_members` (now in the `supabase_realtime` publication, which it wasn't before — see below) filtered to that chat. "Přečteno" is deliberately 1:1-only, shown under your own last message when the other participant's `last_read_at` is at or past that message's `created_at` — the same scope decision as the online dot above it: a group's "read by N of M" is a different, harder display problem that wasn't asked for here.

**Reactions are a genuinely new table, `message_reactions`, not a column on `messages`** — one message can carry reactions from several people and several different emoji at once, which a single column can't represent. `chat_id` is deliberately denormalized onto the table (not just `message_id`, which would require a join to know which chat a reaction belongs to) for two reasons that both come from the same constraint: Realtime `postgres_changes` filters can only match a column directly on the subscribed table, not through a join, and the RLS policies stay exactly as simple as `messages`' own (`jsem_clenem(chat_id)`) instead of a slower `EXISTS` subquery on every read. The client never gets to set `chat_id` itself — a `BEFORE INSERT` trigger (`vynut_chat_id_reakce`, plain `SECURITY INVOKER` with a pinned `search_path` after the linter caught it running without one) looks it up from the target message and overwrites whatever the client sent; Postgres evaluates a row's `WITH CHECK` policy *after* `BEFORE` triggers run, so the RLS check downstream always sees the trigger's trustworthy value, never the client's. Reacting requires the same `jsem_clenem`/`je_skutecny_ucet`/`not je_zabanovan_ze_social` triad `messages` INSERT already requires, plus `not je_blokovan_se_mnou(sender_id)` of the message being reacted to — the same symmetric-blocking posture the rest of Social already applies everywhere. `EMOJI_REAKCI` (`types.ts`) is a fixed six-emoji set, not a picker — the same "pevná sada, ne libovolný vstup" restraint as `IKONY_SKUPIN` for group icons. A double-tap on the same emoji hits the table's `unique (message_id, user_id, emoji)` constraint (Postgres error `23505`), which `pridatReakci()` treats as a success, not a failure — the reaction the user wanted already exists.

**Reply quoting only ever looks inside the messages already loaded on screen — it doesn't fetch the original.** `messages.reply_to_id` is a plain nullable self-reference, no RLS change needed (it's just one more column the existing INSERT check already covers). `ChatView.tsx` resolves the quoted preview by searching the current `zpravy` array for the id; if the original was paged out of view (older than what "Načíst starší zprávy" has loaded so far) or was deleted, it falls back to a generic "Odpověď na dřívější zprávu" line instead of firing a second query per quoted message — consistent with this file's running preference for "browse what's already loaded, don't multiply round-trips for a preview."

**Muting is a plain boolean on your own `chat_members` row, and it only ever suppresses the *summed* badges — never a chat's own row-level unread count.** `ztlumitChat()` is a one-column `.update()` gated by the same `user_id = auth.uid()` policy `last_read_at` updates already use, no new policy. What actually changes is `inbox.ts`'s `prepocitat()` (excludes muted chats from the app-wide badge sum) and its realtime message handler (skips the OS notification for a muted chat's message) plus `SocialModule.tsx`'s own "Chaty" tab badge — but `ChatyPanel.tsx`'s per-row `ch.neprectene` is untouched, so opening the chat list still honestly shows what's actually unread in a muted chat, just without the noise everywhere else. `inbox.ts` caches the muted-chat-id set at module scope, refreshed on every `prepocitat()` call, so the realtime message handler (which only receives a bare message row, not chat metadata) doesn't need an extra query per incoming message to know whether to notify.

**`chat_members` joined the `supabase_realtime` publication for the first time in this pass** (alongside the brand-new `message_reactions`) — it had never needed to broadcast before, since nothing previously depended on seeing another member's row change live. Both follow the same "why messages/friendships/oznameni are already in it" reasoning documented above: Realtime enforces the identical RLS a normal read would, so an unfiltered publication membership still only ever delivers rows the subscriber could already read directly.

**Verified against real production Supabase data via role/JWT impersonation** (a genuine member reacting successfully with `chat_id` auto-filled correctly by the trigger; a non-member rejected by the trigger itself before RLS even runs; `anon` rejected outright with a permission error on `jsem_clenem`; one member unable to delete another's reaction; one member unable to mute another's `chat_members` row) **and via a temporary Playwright spec** (deleted after passing) covering all four features against the mocked backend in one flow, including mutating the mock's `chat_members` data mid-test to prove "Přečteno" actually flips once the simulated participant's `last_read_at` catches up. `tests/e2e/helpers.ts`'s `PATCH`/`DELETE` mock handlers used to filter only by an `id` query param — harmless for every call this codebase had made until now, since they all happened to delete/update by id, but `ztlumitChat`'s `chat_id`+`user_id` filter and `odebratReakci`'s `message_id`+`user_id`+`emoji` filter both filter by other columns instead. Unfixed, a `PATCH`/`DELETE` with no `id` param would have silently matched *every* row in the table (the old code's `!id` fallback), which would have broken the read-receipts test in a way that looked like a pass — the mock generalizes to arbitrary `eq.` filters now, the same shape `GET` already had.

**Social Fáze 2 (first slice) gave the public profile a real photo and a visible bio — both turned out to need far less new work than the phase name suggested, because the data was already there.** `profiles.motto` has round-tripped through cloud sync (`core/supabase/sync.ts`) since before Social's public profile dialog existed; `precti_verejny_profil()` just never returned it, because there was nowhere to show it until now. Same story for the avatar plumbing — `SocialProfil.avatarUrl` and every `nactiProfily`/`nactiChaty`/`nactiVerejnyProfil` query already selected `avatar_url`; the column existed and the client already read it, it just never held anything, because nothing ever wrote to it. The two real gaps closed here were narrow: teach `precti_verejny_profil()` to also return `motto`, and give the app an actual way to put a photo *into* `avatar_url` — this project's first use of Supabase Storage.

**The `avatary` bucket is public, the same sensitivity level this file already accepted for name+photo the moment search-by-name shipped** — a deliberate choice over a private bucket with signed URLs, made explicitly (not assumed) because it trades continuous signed-URL refresh complexity for a decision this codebase had effectively already made. Storage's own RLS applies to `storage.objects`, not to a `public.*` table, but the shape is identical to everything else in this file: own-folder only for `INSERT`/`UPDATE`/`DELETE` (`(storage.foldername(name))[1] = auth.uid()::text` — the path is always `<user_id>/avatar.jpg`, a fixed name so a re-upload overwrites in place via `upsert: true` rather than piling up old versions with nothing pointing at them), `SELECT` open to everyone (redundant with the bucket's own public-read behavior, kept anyway for `.list()` calls and for consistency with how every other table's RLS in this file is stated explicitly rather than left implicit).

**`core/supabase/avatarStorage.ts` is deliberately its own small module, not folded into `social/api.ts`.** The comment on `api.ts` says it's the only place Social talks to Supabase — this isn't Social-specific, it's profile infrastructure `ProfilModule.tsx` calls directly (same layering as `core/supabase/sync.ts` itself). `fileToResizedBlob` (`src/utils/image.ts`) is a new sibling to the pre-existing `fileToResizedDataUrl`, sharing a factored-out canvas-resize step — a data URL (base64) would inflate the upload by roughly a third for no reason once the destination is a real byte-oriented endpoint instead of a JSON/localStorage string. The *existing* local avatar (`ProfilModule.tsx`'s `updateProfile({ avatar: dataUrl })`, a `secureStorage` data URI, unrelated to and unchanged by this feature) still exists and still works exactly as before — offline, instant, no account needed. Picking a new photo now does both in one gesture: the local data URI updates immediately (unchanged behavior), and — only when signed in with cloud configured — the same file is separately resized larger and pushed to Storage, becoming the photo *other people* see in Social. Losing the network mid-upload only fails the second, additive step; the local photo the user is looking at already updated regardless, matching this file's standing rule that a cloud feature is a bonus, never a precondition.

**`SocialAvatar.tsx` gained an `avatarUrl` prop, threaded through every call site across `PratelePanel.tsx`/`ChatyPanel.tsx`/`SpravaSkupinyDialog.tsx`/`TajnyChatPanel.tsx`/`VerejnyProfilDialog.tsx`** — mechanical but not automatic: the colour ring around the photo stays (same conic-gradient/mask technique, now framing an `<img>` instead of an initial), because it's still how a friends list tells rows apart at a glance, photo or not. A blocked (`tlumeny`) row keeps showing the plain initial even when `avatarUrl` is present — the same "blocked = no distinguishing colour" reasoning `avatarColor.ts` already states, extended to not show their photo either. `ChatyPanel.tsx`'s chat-list row is the one call site with no direct `SocialProfil` handy for a group chat; a 1:1 row reads its avatar from `chat.ucastnici[0]`, a group keeps the existing icon/`#` treatment, since a group has no single photo to show.

**Moderation for uploaded photos reuses the existing report pipeline rather than adding anything new, per explicit instruction — there is no budget here for image classification.** `DuvodNahlaseni` gained one value, `nevhodne_foto` ("Nevhodná profilová fotka") — a plain addition to an already-unconstrained `text` column (`reports.reason` has no `CHECK`), so no migration was needed for it, unlike the Storage policies above. A moderator resolving that report today only has the existing tools (ban from Social, ban from the app) — there's no "delete just the photo" action yet, since nothing asked for one; flagged here as the natural next gap rather than built speculatively.

**Verified against real production Supabase data**: `precti_verejny_profil()` now returns `motto` for a real authenticated, non-blocked caller and still returns nothing for `anon` (the pre-existing guard, unchanged); `storage.objects` RLS lets a user insert into their own `<uid>/avatar.jpg` path, rejects the identical insert aimed at someone else's folder, and rejects `anon` outright — the same three-shape check this session applies to every new RLS surface. **And via a temporary Playwright spec** (deleted after passing): a friend row and the public profile dialog both render the mocked `avatar_url` as a real `<img>`, not the initial-letter fallback; the dialog shows the mocked bio text; the report dialog's reason list includes the new option. The upload network call itself (`supabase.storage.from().upload()`) was not exercised end-to-end in the mock — `tests/e2e/helpers.ts` intercepts the REST/RPC shape, not Storage's distinct upload response contract, and `avatarStorage.ts`'s own try/catch already guarantees a failed or unmocked upload degrades to "local photo only, cloud step silently skipped" rather than a crash, consistent with how every other optional cloud path in this file is verified.

**The same pass added a second slice on top: banner, a longer bio, avatar frames, pinned badges, mutual-friend counts, friend suggestions, and a shareable profile link with QR — all still free, no paid infrastructure, because none of them needed anything beyond another `profiles` column, a `SECURITY DEFINER` function shaped like the ones already in this file, or a client-only library.**

**Bio, banner, avatar frame and pinned badges all needed the exact same "text field that mirrors to `profiles` for others to see" shape motto already has — so they ride the existing `CloudSnapshot`/`mergeSnapshots`/`cloudSync.ts` pipeline instead of a new one.** `bio`/`frameId`/`pinnedBadges` joined `ProfileData` (`useProfileData.ts`) and `CloudSnapshot` (`core/supabase/types.ts`) alongside `displayName`/`motto`, with the identical "local non-empty wins, else remote" merge rule (`merge.ts`) — a fourth field going through a proven mechanism, not a parallel one. `bannerUrl` is the one exception: like `avatar_url`, it's set by a Storage upload writing straight to `profiles.banner_url` (`core/supabase/avatarStorage.ts`'s `nahrajDoStorage`, refactored out of the avatar-only version to share the resize/upload/write steps for both), never by the debounced snapshot push — two independent write paths for the same column would race.

**`pinned_badges` taught a real lesson about trusting a client-writable column: the first version of `precti_verejny_profil()` returned it verbatim, which meant a user could claim a badge they never unlocked.** `profiles.pinned_badges` has a plain self-row `UPDATE` policy (same as every other profile field), so nothing stops a client from writing any badge id into it — the app's own picker (`RewardModule.tsx`) only ever offers unlocked badges, but that's a client-side courtesy, not a guarantee. Caught by testing the actual read path against real data (an unearned badge came back in the result) before shipping, not by inspection — the fix filters `pinned_badges` against `user_badges` inside the function itself (`unnest(...) where b in (select badge_id from user_badges where user_id = cil)`), so what the client stores is only ever a *request* to show a badge, and what ships to a viewer is only what that user actually has, verified again afterward with a real unlocked-vs-not pair.

**Avatar frames are a cosmetic recolor of the ring `SocialAvatar.tsx` already draws, not a new component.** The conic-gradient ring already exists (colored per-user via `avatarColor.ts`); a "frame" (`social/avatarFrames.ts`) is just a fixed `{a, b}` color pair overriding those two CSS custom properties, the same mechanism, different input. VIP-gating reuses `cosmetics.premium` exactly like app themes do — but with a twist themes never needed: a theme only ever applies to the *current* user (`useHasPermission` works fine), while a frame is displayed on *someone else's* avatar, where no live permission hook exists for a stranger. `resolveActiveFrameId(frameId, role)` solves this the way `precti_verejny_profil()`'s own `role` column already does the work — that role string is already time-limited correctly server-side (`valid_until is null or valid_until > now()`), so evaluating a VIP frame's eligibility from it, client-side, at render time, gets the same "expired VIP silently loses the cosmetic, no active downgrade needed" property `resolveActiveThemeId` established for themes, without inventing a second server round-trip to ask "is this stranger still VIP?"

**Mutual-friend counts and suggestions both needed a `SECURITY DEFINER` function for the same reason `precti_verejny_profil()` does — your own RLS on `friendships` only lets you read rows *you're* a party to, never a stranger's.** `pocet_spolecnych_pratel(cil)` returns only a number, deliberately — the running rule in this file (`je_muj_pritel`, `je_blokovan_se_mnou`) is never to expose a friend *list* belonging to someone else, only yes/no or count questions about it, and a mutual-friends count answers "how well do we know each other" without ever naming who. `navrhy_pratel()` is capped at 8, the same restraint `hledej_podle_jmena`'s cap of 20 already established for any function that could otherwise be used to enumerate the social graph at scale. Both are revoked from `anon`/`PUBLIC` and granted only to `authenticated`, checked directly against `anon` this time before shipping — the exact class of mistake (`ma_pravo_na_tajny_chat`, `precti_verejny_profil`'s anon guard) this file has now caught three times, caught here by habit rather than by accident.

**The friend code finally has an owner-facing screen again, and it's a materially different feature from the one that was removed, not a revival of it.** `PratelePanel.tsx`'s old "TVŮJ KÓD" UI was deliberately retired when Social moved to search-by-name (see above) — bringing back a code-entry box for *discovery* would undo that decision. **Scanning someone else's QR follows the exact "feature-detect, offer a typed fallback" shape `BuddyOverlay.tsx` already established for iOS Safari's missing `SpeechRecognition`.** `SkenovatKodDialog.tsx` tries `window.BarcodeDetector` (Chrome/Edge/Android; not Firefox/Safari, hence `social/barcodeTypes.d.ts` declaring just the slice of the interface used, the same reasoning as `speechTypes.d.ts`); when it's missing, or camera access fails, a manual code-entry input takes over instead of a dead end — nobody is left without a way to add a friend just because their browser or a denied permission got in the way of the faster path. **Verified against real production Supabase data**: `pocet_spolecnych_pratel`/`navrhy_pratel` both return correct results for a genuine triangle of friendships (temporarily inserted, then removed) and are unreachable by `anon`; the `pinned_badges` fix confirmed against a real `user_badges` row (unlocked badge passes through, a claimed-but-unlocked one is silently dropped); the `pripnute_odznaky_max_3` `CHECK` constraint rejects a fourth id from either the client or a direct write. **And via a temporary Playwright spec** (deleted after passing): the own-profile card renders the real friend code and a QR `<img>`; a friend's dialog shows bio, the equipped frame's ring class, and one pinned-badge pill; the suggestions section shows a mocked candidate with its mutual-friend count; a `/social?kod=...` URL opens the right profile automatically. The camera-based scanner itself (`SkenovatKodDialog.tsx`'s `BarcodeDetector` path) was not exercised live — no camera in this sandbox — verified by code review and by the same feature-detection shape already proven for speech recognition instead.

**The záložky (tab) row and the "MŮJ PROFIL" card were both flagged by a real screenshot as cramped and hard to tap — five/six `flex: 1` tabs in one row forced tiny text that wrapped ("Tajný chat" broke onto two lines) with no room between tap targets.** Fixed two ways at once, both explicitly asked for. First, `.social-zalozky` switched from `flex:1`-squeezed items to a horizontally scrolling row (`overflow-x: auto`, `scroll-snap-type: x proximity`, each `.social-zalozka` back to its natural text width) — the same scrolling idiom the game hub's character carousel already established (`TvorbaPostavy.css`), not a new pattern. Second, and requested explicitly ("chci profil jako že klikneš a uvidíš profil, to má Instagram řešené") — the QR/friend-code sharing block stopped being a card wedged above "NAJÍT LIDI" in the Přátelé tab and became its own "Profil" tab, `MujProfilPanel.tsx`, the same mental model as Instagram's own profile screen: tap it, see your own profile, not someone else's list with your own card mixed in.

`MujProfilPanel.tsx` renders the same visual pieces `VerejnyProfilDialog.tsx` already draws for a *stranger's* profile (banner/avatar+frame/role tag/motto/bio/pinned badges/level bar/streak, sharing the same `.social-profil-*` CSS classes, wrapped in a new `.social-card--profil` modifier that gives the card the dialog's `1rem` padding so the banner's `-1rem` bleed math still lines up outside a dialog) — but unlike that dialog, it never calls `precti_verejny_profil()` over the network. For *your own* profile the data is already sitting in local stores (`useProfileData`, `useGamificationStore`, `useActiveRole`), so building it from those is both simpler and matches "offline-first" — the same reasoning `avatarFrames.ts`'s own comment on `resolveActiveFrameId` already flagged ("pro VLASTNÍ avatar appka může zavolat useHasPermission přímo," now realized via `useActiveRole` instead). It also gained one thing the dialog can't offer for a stranger: an "Upravit profil" button that navigates straight to `/profil`, since seeing your own profile without a way to edit it would be a dead end the dialog's "someone else's" version never has.

The QR/kód sharing block (`social/shareLink.ts`'s `profilOdkaz`, the `qrcode` package, `SkenovatKodDialog.tsx`) moved out of `PratelePanel.tsx` into `MujProfilPanel.tsx` unchanged in content — same code, new home. `PratelePanel.tsx` keeps only what's actually about *other* people: search, suggestions, requests, the friends list. A new `user` icon (single figure, distinct from `users`, the group icon "Přátelé" already uses) was added to `SocialIcon.tsx` for the tab.

**A real screenshot of the new Profil tab caught a second, unrelated bug: a locally-uploaded avatar photo bled out below the circular ring instead of cropping to it, tens of pixels of the photo spilling into the motto/level rows underneath.** `.social-avatar`'s box comes from `inset: 3px` alone, no explicit `width`/`height` — that's fine for the plain `<span>` initial (a non-replaced element, which stretches to fill an inset box with all four sides set), but the photo path renders a real `<img>`, a *replaced* element, and replaced elements size themselves from their own intrinsic aspect ratio when width/height aren't explicit, ignoring the geometric gap between the insets entirely — a classic, easy-to-miss CSS distinction between replaced and non-replaced elements. A tall, narrow source photo (the common case for a phone screenshot chosen as an avatar) rendered at its own intrinsic ratio instead of clipping to the 50×50 circle. Fixed with one line: `.social-avatar--foto` now also sets `width: 100%; height: 100%` explicitly, which forces the replaced element to size itself from the box (not its intrinsic ratio), letting the pre-existing `object-fit: cover` actually do its job. Confirmed with a temporary Playwright spec (deleted after passing) seeding a deliberately tall SVG data URI straight into `secureStorage`'s encrypted format and reading the rendered `<img>`'s real bounding box: 56×196 before the fix, 56×56 (matching the wrap exactly) after.

**Přátelé stopped being its own tab entirely and folded into Profil, on top of a straight reorder — both explicitly asked for in the same pass.** `PratelePanel.tsx` (search/suggestions/requests/friends list) is now rendered *by* `MujProfilPanel.tsx`, appended right after the "MŮJ KÓD" sharing block, rather than being a sibling `SocialModule.tsx` switches between — one `<PratelePanel>` render call, nested `.social-panel` flex column inside another, no new wrapper needed since the nesting is visually harmless (same gap, same card styling). `MujProfilPanel` gained an `onOtevritChat` prop to pass through to it (the "Napsat" action on a friend row still needs to open the real chat). The friend-request badge count (`cekaZadosti`) moved with it — it now lights up the `profil` tab id in `SocialModule.tsx`'s odznak switch, not a `pratele` id that no longer exists. `ZALOZKY` dropped the `pratele` entry and `profil` moved from last to first — with search-and-friends now living inside it, Profil is the de facto home screen of Social, not a sharing card tucked in at the end, so the default active tab (`useState<Zalozka>`) changed from `'pratele'` to `'profil'` too.

**Social is being redesigned in explicit phases (requested as such), the first being a full navigation rework: a bottom tab bar (Instagram/TikTok-style) in place of the old horizontal row of tabs above the content.** This isn't cosmetic-only — it's also what finally, structurally, retires the wrapping/crowding problem the horizontal-scroll fix (above) only patched: five or six `flex: 1` labelled pills fighting for one row's width was the root cause, and a bottom bar's icon-first, one-word-label items never had that problem to begin with, so `.social-bottom-nav`'s items go back to plain `flex: 1` with no scroll container needed. `.social-nav-item` stacks `SocialIcon` above a small label (`.social-nav-icon-wrap` wrapping just the icon, so the unread-badge — `.social-nav-odznak` — anchors to the icon's own corner, not the whole button); the active tab tints cyan, matching the app's existing selection-state colour everywhere else. The bar itself reuses the Hub's own already-safe-area-tested `.hub-bottom-bar` shape verbatim rather than inventing a second pattern for the same problem: `margin-top: auto` inside `.social-page`'s flex column pushes it to the bottom with no scrolling needed, `position: sticky; bottom: 0` keeps it there once content *does* scroll, and a `::before` pseudo-element bleeds a gradient backdrop past the page's own padding (negative `inset` matching `.social-page`'s exact padding numbers) so content sliding underneath fades rather than hard-cuts. `.social-toast`'s fixed `bottom` offset moved from `1.25rem` to `4.5rem` for the same reason — it used to float safely in empty space at the bottom of the page; now that space is occupied by real navigation, and the old offset would have sat the toast on top of the tab bar. The top bar lost its subtitle and breathing hero emoji in the same pass — both belonged to the old top-heavy layout, and a bottom-nav'd screen only needs a bare wordmark up top, the same minimal header shape Instagram/TikTok themselves use. Verified with a temporary Playwright spec (deleted after passing): four nav items render (no horizontal scroll needed even conceptually now), tapping between them switches the active tab and its highlighted state correctly, and a full-page screenshot confirmed the bar sits flush at the bottom with the gradient backdrop reading correctly against scrolled content. Further Social redesign phases — Stories (24h posts), photo/video messages in chat, voice messages — are planned as separate, later passes, not bundled into this one.

### Roles & shop

`src/core/role/` holds the role system. Each role is its own folder exporting a single `RoleDefinition` (`user/`, `vip/`, `moderator/`, `admin/`), and `registry.ts` is the only place they are enumerated — adding a role means a new folder plus one line there. **Nothing branches on a role's name**: every check goes through a `Permission` (`useHasPermission('cosmetics.premium')`), so a new role never means hunting for `roleId === 'vip'` comparisons. Import from the `@/core/role` barrel, not from the individual files.

VIP is a subscription, so a `RoleAssignment` carries `validUntil` (`null` = no expiry). **Expiry is evaluated on read, never stored** — `useActiveRole()` runs `resolveActiveRoleId` and silently returns `user` once the date has passed. A stored "still valid" flag would go stale while the app isn't running and nobody would correct it. `roleUtils.ts` holds that math as pure functions; `extendValidity` counts from the end of the running period, so renewing early never shortens what the user paid for. Corrupt or unreadable state always falls back to `user` — the safe direction is to grant nothing.

`FEATURE_GATING_ENABLED` in `registry.ts` is deliberately `false`: the `features.premium` permission exists but nothing hides behind it, because content users have today must not disappear behind a paywall. Only newly added features should ever be gated.

Credits live in `useWalletStore` (`core/store/`, because they are spent outside the shop too). The shop itself is `src/pages/shop/` — `catalog.ts` is the hand-maintained offer (prices in **haléře**, integers only), `useShop.ts` the logic, and `ShopModule.tsx` renders it.

**No purchase completes today, on purpose.** There is no payment gateway, and money-backed state cannot be decided by the browser: `secureStorage` is XOR obfuscation, so a user can hand-edit their own VIP or balance. Every purchase therefore funnels through the single `purchase()` in `useShop.ts`, which returns `{ status: 'unavailable' }` for anything costing money — wiring a gateway means changing that one function, not the components. For the same reason both `schoolbuddy-role-storage` and `schoolbuddy-wallet-storage` are `restorable: false` in `BACKUP_STORES`: an edited backup must not be able to grant VIP. When a real backend arrives, these stores become a *cache* of what the server says, never the authority.

### Admin panel (`src/pages/admin/`)

`/nastaveni` shows an "Administrace" section, visible only with the `admin.panel` permission (so only `ADMIN_ROLE`), linking to `/admin`. It's the app's **first route-level permission gate** — every other route only checks `dovnitr` (signed in), this one also checks `useHasPermission('admin.panel')` in `App.tsx` and redirects a non-admin to `/nastaveni`. That gate protects the UI only, same warning as everywhere else in `core/role/`: a user can edit their own client-side role. What actually protects the data is that every call the panel makes re-checks on the server — `jsem_admin()` (SQL, `SECURITY DEFINER`) backs both `admin_prehled()` and the reports RLS it shares with moderators, so a spoofed local role sees an empty panel, not real data.

**`jsem_admin()` is deliberately its own function, not a reuse of `jsem_moderator()`.** The latter passes both `'moderator'` and `'admin'` — right for reading reports, wrong for `admin_prehled()`'s database-wide aggregates (total accounts, messages sent), which a moderator must not get just because they can also see reports.

**A real moderator had permissions in the database but no way into the UI at all, until this was caught and fixed.** `MODERATOR_ROLE` has carried `moderation.content` since the role system's early days, and every report-reading/resolving RPC has always accepted `jsem_moderator()` — but `App.tsx`'s `/admin` route and the "Administrace" entry point in `/nastaveni` both checked only `admin.panel`, which only `ADMIN_ROLE` grants. A signed-in moderator could call `nacti_hlaseni`/`vyridit_hlaseni` from a console and it would work, but there was never a screen that let them get there normally — the permission existed on paper and nowhere in practice. Both gates now also accept `moderation.content`; `AdminModule.tsx` decides what to render from the same two permissions rather than trusting the route to have sorted it out, filtering `ADMIN_TABS` down to just SocialReport and swapping the header to "Moderace" when `admin.panel` is absent — so a moderator lands on exactly the one screen the database has always let them use, nothing more (Přehled's aggregates, Uživatelé's role changes, and Audit log stay behind `admin.panel` in the UI, matching how they're already gated in the database). This is UI-only, same caveat as the rest of this section: the actual boundary was always `jsem_admin()`/`jsem_moderator()` in Postgres, not the route.

**The panel opens on a menu, not straight into the first section.** A flat row of seven tabs treated every section as equally weighted, but they aren't — Přehled is a glance-at-it dashboard, Uživatelé is an action that shouldn't happen by accident. `ADMIN_TABS` (`types.ts`) now carries a `popis` (one-line description) and a `permission` per entry (`'moderation.content'` or `'admin.panel'`, the same pair everything else in this section already keys off), and `AdminModule.tsx` renders them as two labelled groups — Moderace first, Administrace under it — each group only appearing when the signed-in role actually has something in it, so a moderator without `admin.panel` sees a single-item Moderace menu, not an empty Administrace heading teasing sections they can't open. Every row also carries a small role-tag pill (reusing `MODERATOR_ROLE`/`ADMIN_ROLE`'s own `icon`/`title`/`tone` from `core/role`, the same colours `ProfilModule.tsx`'s own role tag already uses, so "this needs Moderátor" reads identically everywhere in the app) naming the lowest role that opens it — derived from the same `permission` field, not a second hand-written label that could drift out of sync. Tapping a row opens that section full-screen with its own back button ("← Zpět do menu"); the top-level "← Zpět do nastavení" only shows on the menu itself. The permission check that used to gate only which tabs render still also gates what actually mounts when a section is open — reading `sekce` out of React state can't be trusted further than that, same reasoning as everywhere else in this file that a client-side role is UI-only.

Seven sections in the menu: **Přehled** (status numbers from `admin_prehled()`, plus a live graph — see below), **SocialReport** (reuses `social/api.ts`'s `nactiHlaseni`/`vyriditHlaseni`/`popisDuvodu` directly rather than duplicating them, keeping "api.ts is the only place Social talks to Supabase" true; each report shows the reported person's raw Supabase id, not just their display name, since bans key off the id and a display name can be changed by its owner at any time), **Notifikace** (broadcast announcements — see below), **Audit log** (who-did-what-when — see below), **Uživatelé** (browse/search any account and change its role — see below), **Systém** (client-caught crash reports — see below), and **Konzole** (a command registry in `commands.ts` — one command today, `appinfo`; adding another is one entry there, not a change to `KonzolePanel.tsx`, which only renders whatever a command returns).

**The "live parameters" graph only has real data for one of its three sources.** Supabase and Vercel both expose load/usage metrics only through their own management APIs, which require a secret access token — and a secret token embedded in this client-only PWA's JS bundle is readable by anyone who opens the network tab, admin-role gate or not (same class of problem as the money-backed stores above, one step worse: this isn't the user's own state, it's a credential to a shared account). Wiring those up for real means a small server component holding the token server-side (a Vercel/Supabase function the panel calls, authenticated) — deliberately unbuilt and, when last asked, deliberately deferred again rather than forgotten. The "Aplikace" source is real and live today — `metrics.ts` samples only what the browser can safely expose about itself (JS heap, Storage API quota, Cache Storage count, online status, build version) on a 3-second timer, capped to the last 20 samples so the sparkline in `PrehledPanel.tsx` shows a trend without the array growing forever.

**Přehled also carries a detailed-analytics layer beneath the single-snapshot stat grid, built entirely from data already in `public.*` — no secret token, unlike the live-parameters graph above.** Three admin-gated RPCs (`admin_rustovy_graf`, `admin_aktivita_podle_druhu`, `admin_top_odznaky`) are separate functions rather than one, because each returns a differently-shaped table and SQL `returns table(...)` can't mix column counts in one response. `admin_rustovy_graf()` is the one function in the codebase that reads `auth.users` directly (schema-qualified, reachable because it runs `SECURITY DEFINER`) rather than going through `public.profiles` like `admin_prehled()` does — `profiles` has no creation timestamp, only `updated_at`, so a growth-over-time chart has nowhere else to read "when was this account created" from; it filters `is_anonymous = false` to keep the pre-login-requirement orphaned anonymous rows (see **Accounts & Social**) out of a chart about real signups. The other two aggregate `activity_counters`/`user_badges` across every user (which miniapps actually get used, which badges actually get earned) — deliberately account-level sums, never per-user rows, so this stays "aggregate analytics," not a user browser. `PrehledPanel.tsx` renders the growth chart by reusing the existing `.admin-graf` bar-chart markup a second and third time (one bar row per metric) and adds a small shared `PruhovyRadek` (horizontal bar) component for the other two — both an unrecognised `ActivityKind` and an unrecognised badge id fall back to showing the raw code rather than silently dropping the row, the same "report the real thing" instinct as the audit log's action-label map below.

**SocialReport shows a repeat-offender count and can delete the reported message directly, both added once moderators could actually reach the panel (see above) and "just ban or dismiss" started to feel thin for the actual job.** The repeat count needs no new query: `nactiHlaseni()` already returns every report a moderator can see, so `SocialReportPanel.tsx` tallies how many target the same `nahlaseny.id` client-side and only shows the badge above one — a first-time report and someone with three open reports against them shouldn't read identically. Deleting the offending message reuses `smazatZpravu()` unchanged (the same soft delete Social's own chat UI uses) — it needed one addition to reach here: `Hlaseni` only carried the reported message's *text*, not its id, because nothing before this needed to act on it, only display it. `zpravaId` is separate from `zprava` in the type on purpose, mirroring the id/name split documented above for bans: a report's target can be identified by id even after its message text is gone.

**SocialReport carries two separate bans, and they live at two different layers on purpose.** "Zakázat Social" only ever needed RLS: `social_bans` is a table nobody can write except `zabanuj_ze_social()` (`SECURITY DEFINER`, admin-gated, same shape as `user_roles`), and the friendship/message/chat `INSERT` policies now also check `not je_zabanovan_ze_social()`. A banned account keeps read access to everything that already existed — banning is "no new writes," not retroactive deletion. "Zakázat celou appku" is a different kind of operation entirely: blocking sign-in isn't something any RLS policy can do, because RLS protects rows, not the auth handshake itself. That needs Supabase's admin API (`auth.admin.updateUserById(id, { ban_duration: '876000h' })`), which needs the **service role key** — a credential that bypasses RLS completely, sensitive enough that it doesn't reuse `api/buddy-chat.ts` and instead gets its own narrowly-scoped function, `api/admin-ban.ts`. That function is deliberately careful about *when* it touches that key: it decides whether the caller is really an admin first, by reading the caller's own `user_roles` row through the normal REST API with the caller's own token (RLS lets everyone read their own role) — only once that passes does it construct the service-role client, so the most dangerous credential in the project is never in scope for the one decision (is this person an admin?) that a spoofed client-side role could otherwise try to influence.

**Notifikace writes into the same `oznameni` table the Hub bell already reads.** There's no separate "admin broadcast" delivery path — `core/notifications/api.ts` is the one place anything talks to that table, and the existing notification bell (`useNotificationItems()` in `pages/profil/components/ProfilNotifications.tsx`, shared by both `ProfilModule` and `AppModule`'s badge count) just merges in whatever it returns alongside the locally-derived items (badges, streak, pending tasks). Announcements are prepended, not appended — they're things the user should notice before their own progress stats. `oznameni` doesn't need a `SECURITY DEFINER` function like `social_bans` or `user_roles` do: an admin broadcasting isn't touching anyone else's row, just inserting a new one, so a plain RLS `INSERT` policy gated on `jsem_admin()` is enough, and `created_by` defaults to `auth.uid()` server-side so a client can't claim someone else wrote it. Every signed-in user can `SELECT` — it's public content, not anyone's private data. Realtime is on (`supabase_realtime` publication), so an announcement posted while a user has the app open lights up the bell without a refresh, same mechanism as friend requests.

**Audit log records every privileged admin/moderator action, and how it gets written there depends on how the underlying action itself is performed — deliberately three different mechanisms, not one.** `audit_log` is a plain table (admin-only `SELECT` via `jsem_admin()`, no write policy for anyone — the same "server decides, client can only read" shape as `user_roles`), fed by `zapis_audit_log()`, a small `SECURITY DEFINER` helper that just inserts a row. (a) An action that's already its own `SECURITY DEFINER` RPC gets one extra line at the end of its existing body — `zabanuj_ze_social()` now ends with `perform public.zapis_audit_log(...)`, so there's no way to call the real ban without also logging it. (b) An action performed as a plain RLS-gated `.update()`/`.insert()`/`.delete()` with no wrapping RPC — resolving a report, posting or deleting an announcement — gets a `SECURITY DEFINER` trigger instead (`zaznamenej_vyrizeni_hlaseni()` on `reports`, `zaznamenej_oznameni()` on `oznameni`), because logging from inside `SocialReportPanel.tsx`/`NotifikacePanel.tsx` would be trivially bypassable by anyone calling the table API directly — a trigger fires no matter how the row changed. (c) An action that isn't a Postgres write at all — `api/admin-ban.ts`'s Auth Admin API call for the app-wide ban, which a database trigger structurally cannot observe — logs explicitly from within the serverless function itself, using the same service-role client that just performed the ban, after the ban succeeds (a logging failure there is only `console.error`-ed, never allowed to undo an already-applied ban). `nacti_audit_log()` is the one read path, admin-gated the same way as `admin_prehled()`, paginated (`pocet`/`posun`, capped at 200 rows) and joining `profiles` twice to resolve both the acting admin's and the target's display names for `AuditLogPanel.tsx` without a second round trip.

**Uživatelé is deliberately not the same thing as Social's friend-code-only discovery, even though both ultimately search `profiles`.** The "no search by name" rule under **Accounts & Social** exists because a plain RLS policy letting any signed-in user read every profile is the same as publishing a directory of children — but admin already has that visibility everywhere else in this panel (`admin_prehled()`'s counts, `SocialReport`'s raw ids), gated by `jsem_admin()`, not by a public policy. `admin_seznam_uctu()` follows the same shape: `SECURITY DEFINER`, admin-gated, gives a name/friend-code substring search plus every stat already visible elsewhere in the panel (XP, level, streak, role) — it does **not** add email or anything not already surfaced somewhere in the admin UI, so it widens *how* an admin reaches existing visibility, not *what* they can see. Role changes go through `admin_nastav_roli()`, which refuses to let an admin change their own role (`cil = auth.uid()` raises) — the same self-target guard `api/admin-ban.ts` already has for app bans, here preventing an admin from fat-fingering themselves out of the panel with nobody else able to undo it. Granting VIP from this panel defaults to `VIP_DURATIONS.month` (the same constant the shop's real purchase flow uses) rather than a separately-invented admin-only duration; the other three roles carry no expiry. `UzivatelePanel.tsx` reuses `zabanujZeSocial()`/`zabanujCelouAppku()` unchanged from `SocialReportPanel.tsx` — the only difference is it can act on any account, not just one that already has a report against it.

**Systém is client-side crash monitoring, and unlike the "live parameters" Supabase/Vercel sources it needs no secret token at all — it only ever reads what already happened inside a user's own browser.** `core/utils/errorReporting.ts` attaches a single `window.addEventListener('error', …)` and one for `unhandledrejection` from `App.tsx`'s setup `useEffect` (same one-time-owner pattern as `setupPWAUpdates`/`startCloudSync`), and inserts into `public.client_errors` — a plain RLS-gated table, not a `SECURITY DEFINER` write: the insert policy just checks `user_id = auth.uid()`, the same "can't claim someone else wrote it" shape `oznameni` uses. It reports nothing without a live session (RLS would reject it anyway, and dropping the report is fine — "offline is the normal case, not the error case" applies here too) and caps itself at `MAX_HLASENI_ZA_RELACI` (5) reports per page load, because a component stuck re-throwing in a render loop could otherwise write thousands of rows in seconds before anyone could react — five is enough to know a build is broken without needing a rate limit on the table itself. Reading is admin-gated the same shape as `audit_log`: `nacti_client_errors()`, no `SELECT` policy for anyone else. `SystemPanel.tsx` flags a report's `build_id` against the viewing admin's own `APP_BUILD_ID` — matching build ids is a hint the bug is still live in what's currently deployed, not something already fixed by a later release.

### Support systém (`src/core/support/`, `src/pages/support/`)

`/podpora` is a real two-way support ticket thread between a user and staff, reachable from a "Podpora" card in `/nastaveni` that every signed-in user sees (unlike the Administrace/Moderace card above it, which is conditional). It is deliberately **one screen for both sides**, not a separate admin-only view: `SupportModule.tsx` checks `useHasPermission('admin.panel')` once and adjusts copy/behaviour (a non-admin gets "Nový tiket" and only their own tickets; an admin gets "Podpora — všechny tikety" and a resolve toggle) — `core/support/api.ts`'s functions serve both, because the real access boundary is RLS, not the component. This mirrors how `AdminModule.tsx` itself decides what to render rather than trusting the route (see **Admin panel** above), and how `SocialReportPanel`/`UzivatelePanel` already reuse the exact same ban functions for two different entry points.

**A ticket and its first message are created atomically through `zalozit_tiket()`, the same "one RPC, not two client-side inserts" shape as `zaloz_chat()`.** Two separate inserts risk the identical orphan-row hazard already documented for chat creation: if the second insert (the message) failed after the first (the ticket) succeeded, the ticket would exist with nothing in it and no policy would let anyone clean it up. Every reply after the first — from either side — is a plain `.insert()` into `support_zpravy`, not a wrapping RPC, because nothing about an ordinary reply is privileged enough to need one.

**`je_od_podpory` is computed server-side in the `INSERT` policy's `WITH CHECK`, never trusted from the client.** The column has to exist so the UI can tell a staff bubble from a user bubble, but a plain boolean sent by the client would let anyone claim their own message came from support. The policy instead requires `je_od_podpory = public.jsem_admin()` — so the value the row ends up with is always the truth about who actually sent it, and a spoofed value simply makes the insert fail rather than lie.

**Resolving a ticket is an explicit admin action, but reopening one is a silent side effect of the user replying — deliberately not symmetric.** `vyridit_tiket()` is admin-gated (mirrors `admin_nastav_roli()`'s shape) and logs to `audit_log` like every other privileged action here. A user's own reply reopening a ticket they see as "Vyřízený" needs no such gate — it's their own ticket — so it happens via a plain `AFTER INSERT` trigger (`oznac_ticket_po_zprave()`) instead: any non-staff message flips the status back to `otevreny` and bumps `updated_at`, so a ticket a user is still stuck on can't silently stay marked "done" just because staff answered it once. A staff reply alone never closes a ticket — closing stays a deliberate click, same reasoning as `vyriditHlaseni()` for reports.

**A staff reply is a privileged action and gets audited, but a user's own message never does** — same asymmetry as the reopen behaviour above, for the same reason: only actions performed *as staff* belong in `audit_log`. Because a reply is a plain insert with no wrapping RPC, the log entry comes from a `SECURITY DEFINER` trigger (`zaznamenej_odpoved_podpory()`, firing only `if new.je_od_podpory`) rather than an inline call — pattern (b) in the three-way logging split documented under **Audit log** above, for the same reason: logging from inside `SupportModule.tsx` would be trivially bypassable by calling the table directly.

**The reply box doesn't wait on Realtime to show the sender their own message.** `sledovatZpravyTiketu()` subscribes the same way `sledovatChat()` does in Social, but `VlakloTiketu`'s send handler also refetches the thread immediately after a successful insert — the same pattern `ChatView.tsx` already uses, and for the same reason: relying solely on the Realtime round-trip to echo a message back to its own sender means a slow or momentarily-dead connection leaves the person who just hit "Poslat" looking at a blank thread with no sign anything happened.

### Buddy voice assistant (`src/buddy/`, `api/buddy-chat.ts`)

Tap the mic in the Hub's bottom bar, or the glowing orb itself, and Buddy becomes a real conversational AI (OpenRouter, chosen because it fronts a wide catalogue of models — including several genuinely free ones — behind one OpenAI-compatible API, no SDK needed) that you can talk to and that talks back.

**`api/buddy-chat.ts` was the first server-side code in the app**, and it exists for exactly one reason: an LLM API key is a real credential, and this is a client-only PWA whose whole JS bundle is public — anyone could pull a key straight out of it and spend against the account it belongs to. There is no way to make that safe by hiding harder; it has to never reach the browser. The Vercel serverless function holds `OPENROUTER_API_KEY` (no `VITE_` prefix — that prefix is precisely what makes Vite inline a variable into the shipped bundle, so this one deliberately doesn't get it) and is the only thing that ever calls OpenRouter; it's a plain `fetch` against their `chat/completions` endpoint (the model, `OPENROUTER_MODEL`, defaults to a free-tier one but is overridable without a code change). `vercel.json`'s SPA catch-all rewrite had to be narrowed to exclude `/api/` first, or the rewrite would swallow every request to the function before it ever ran. `api/admin-ban.ts` (see **Admin panel**) later reused that same exclusion and the same never-`VITE_`-prefix rule for its own, even more sensitive key.

The function still isn't open to the internet: it requires a valid Supabase session token (verified against `/auth/v1/user`) before it will spend a single token of the free quota. That's access control, not the per-user daily cap that was explicitly declined for v1 — an unauthenticated proxy risked the shared free-tier quota getting exhausted or the key throttled by randos finding the endpoint, hurting every real user, not just the requester.

**The conversation is turn-based ("walkie-talkie"), not continuously listening, on purpose.** `useBuddyVoice.ts` never has the microphone and speech synthesis active at the same time — recognition only starts on an explicit tap and stops itself when the sentence ends; Buddy's own spoken reply cannot therefore be picked back up by the mic and answered to, which is exactly the feedback-loop failure mode a hands-free design would risk. Tapping the mic again while Buddy is still talking interrupts the speech and starts listening immediately, so a "kolo" (turn) always ends in one of these ways, never both open at once.

**Speech synthesis is known to be flaky across browsers** — an utterance can occasionally fire neither `onend` nor `onerror` (observed for real: this sandbox's headless Chromium has zero installed TTS voices at all, so the "mluví" state couldn't even be watched directly here). Without a fallback, that would leave the state stuck on `mluvi` with the mic looking locked. `promluv()` in the hook sets a backup timer (scaled to the reply's length, 4–20 s) that forces the state back regardless, cleared immediately by a real `onend`/`onerror` when one does arrive.

Speech recognition (`SpeechRecognition`/`webkitSpeechRecognition`) has no TypeScript types in the DOM lib because it's still non-standard — `src/buddy/speechTypes.d.ts` declares only the surface the hook actually uses. It also has **no support at all on iOS Safari**, so `BuddyOverlay.tsx` always renders a typed-message fallback alongside the mic button, not only when recognition is unavailable — the same input path serves "can't talk right now" (a quiet classroom) as much as "can't talk at all" (an iPhone).

Conversation history lives only in the `useBuddyVoice` hook's React state, not in a persisted store — it resets on close by design (an explicit choice: Buddy remembers the running conversation, not a diary), and the hook is owned by `Hub.tsx` itself rather than by `BuddyOverlay`, because the orb needs to react to Buddy's state (`hub-orb--posloucha`/`--premysli`/`--mluvi`, reusing the orb's existing breathing/rotation animations at different speeds rather than inventing new ones) even before the overlay has been opened for the first time.

### Game hub (`src/game/`)

`/hra` is being rebuilt in stages as an actual RPG layer, not the procedurally generated 3D city that used to live here (that whole `scene/` tree — Three.js city, walls, castle, forest — was deleted outright rather than kept around half-connected to a new design; nothing in it survived, since a launcher screen and an RPG have essentially nothing in common to reuse). Character creation, the world map and a first playable card-battle location (the Arena) ship today; the rest of the location content (a dungeon to fight through, a market to buy from, the capital's story line) is a deliberately separate next step — every pin that isn't the Arena still opens a bottom sheet saying so instead of a half-finished feature.

**Every game-hub screen owns its full CSS in its own file; `GameModule.css` holds only the one rule (`.game-back-btn`) actually shared between them.** `TvorbaPostavy` learned this the hard way: it never had its own stylesheet, it just relied on classes that used to live in `GameModule.css`. When that file got cleaned down to just the back button during the map step, the comment claimed every screen already had its own CSS — false for this one — and its `.tp-*` rules vanished with nothing left importing them, so the character picker shipped to production with no styling at all (cards, icons, everything ran together as unstyled text) until a user screenshot caught it. The fix was `TvorbaPostavy.css`, built the same way `MapaSveta.css`/`Souboj.css` already were. The lesson stuck as the comment at the top of `GameModule.css`: before deleting a rule because "the screen has its own file now," check it actually does.

**Characters are a roster, not a single permanent choice.** `useGameCharacter.ts` persists `postavy: PostavaId[]` — every template the player has created, in creation order (`core/utils/gameCharacterValidation.ts` filters out unknown ids item-by-item rather than failing the whole array, so one corrupted entry doesn't wipe the rest of the roster; a `migrate` step upgrades the older single-`postavaId` shape into a one-item roster so nobody's earlier pick just vanishes). Each of the five templates can appear at most once — `vytvoritPostavu` is a no-op if the id is already in the roster, so there's no need to disambiguate two identical "Aryn" entries with nothing to tell them apart. `smazatPostavu` removes one **and its level progress with it** — the one exception to "nothing else is lost" elsewhere in this section: XP/credits/badges stay account-wide in `core/store`, but a character's own level and skill points are that character's save data, and deleting the character deletes the save.

**Leveling is per-character, deliberately not folded into the account-wide XP in `core/store`.** `leveling.ts` holds the whole system as pure functions/constants (`PostavaProgres`, `xpProDalsiUroven`, `pripocistXp`, `bojoveBonusyZProgresu`) so the math is unit-testable without a store or a component; `useGameCharacter.ts`'s `progres: Record<string, PostavaProgres>` just calls them. A win in `Souboj.tsx` feeds XP to *both* systems side by side — `recordAction('battle', xp)` for the account (badges, the app-wide level) and `pridatXpPostave(postava.id, xp)` for that one character — neither replaces the other. `pripocistXp` can carry a big reward across more than one level at once (a dungeon clear is worth more XP than one arena win) and awards one skill point per level; the curve (`40 + (uroven-1)*25`) and the cap (`MAX_UROVEN = 10`, `MAX_DOVEDNOST_RANK = 3`) are tuned so a maxed-out character has spent exactly as many skill points as levels gave it (9 levels × 1 point = 9 = 3 nodes × 3 ranks) — no leftover currency with nothing to spend it on. The three skill nodes (Výdrž/Síla/Přesnost) stack additively with the shop's bonuses from the same stat in `useSouboj.ts` — a level's automatic HP gain, a skill node's HP rank, and an owned shop elixir's flat HP are three independent numbers summed once into `maxVydrz`, not three separate systems fighting for the same slot. Tapping a character's badge in the map's top bar (`.mapa-postava-znacka`, a `<button>` showing `Lv N`) opens `Hrdina.tsx` — see below for what that screen actually contains; the roster picker (`VyberPostavy`) shows the same level as a read-only badge via `PostavaKarta`'s optional `uroven` prop, so a level is visible before you even commit to playing that character this session.

**`Hrdina.tsx` is one screen for everything about the character you're currently playing — portrait, effective combat statistics, a shortcut into the shop, and the skill tree — replacing what used to be a skill-tree-only `Dovednosti.tsx`.** Those four things used to be scattered (a card's own numbers in `postavy.ts`, purchased bonuses only visible inside `Obchod.tsx`, level/skill points only inside the old `Dovednosti.tsx`) with nowhere that showed the *combined* picture. The Statistiky section doesn't recompute anything of its own — it calls `vypocitejBojoveStatistiky(postava, progres, ownedItems)`, a pure function pulled out of `combat/useSouboj.ts` and exported from there on purpose: it's the exact same calculation the hook uses to run a real fight (base stats + level/skill bonuses from `leveling.ts` + owned shop items from `useWalletStore`), so what the character card shows can never drift from what combat actually does with those numbers — one source of truth instead of two. The Vylepšení section is a shortcut, not a duplicate: it counts `ownedItems` against `PREDMETY` (filtering out `useWalletStore`'s other, unrelated owned ids — cosmetic Shop items live in the same store) and opens the real `Obchod.tsx` on tap, wired through `GameModule.tsx`'s existing `obchodOtevren` state so leaving the shop lands back on Hrdina, not the map — `obchodOtevren` is still checked before `hrdinaOtevren` in the render order there for exactly that nesting to work. Reachable two ways with the same destination — the map's character badge and the map's own menu (below) — which is a pattern this codebase already uses elsewhere (`SocialReportPanel`/`UzivatelePanel` reusing the same ban functions).

**The map's floating menu (`.mapa-menu-fab` — the ☰ button, bottom-right of `MapaSveta.tsx`) is the first piece of chrome on the map that isn't a pin.** It opens a small tile grid (`.mapa-menu-mrizka`) reusing the map's existing sheet-overlay styling; it shipped with a single tile (Hrdina) and has grown by exactly one `.mapa-menu-dlazdice` button per feature since — Questy, then Batoh (Fáze 6) — no layout rework needed either time (`flex-wrap` already handles more tiles). Opening the menu clears any open location sheet first (`setOtevrena(null)`) so the two overlays never stack; the reverse never needs a symmetric guard because the sheet's own full-screen backdrop already renders after the FAB in the DOM and sits above it in z-index, which is enough to block taps through to it while a location's sheet is open.

`GameModule.tsx` reads the roster on every visit to `/hra` and picks a screen: empty → `TvorbaPostavy` (create the first one); non-empty and nobody chosen yet for *this* visit → `VyberPostavy` (pick who to play, or add/delete from the roster); chosen → `MapaSveta`. **Who's playing is deliberately session-only React state, never persisted** — closing `/hra` and reopening it asks again on purpose, which is what makes "try a few characters" actually work; a remembered last-pick would need its own explicit "switch character" affordance instead. `TvorbaPostavy` is a controlled, reusable screen now (`dostupnePostavy`/`onVytvoreno`/`onZpet` as props) rather than assuming it's always creating the very first character, so the same component serves both "create my first character" and "add another to the roster" without duplicating the card grid. `PostavaKarta` is the card itself, shared between `TvorbaPostavy` and `VyberPostavy` — its optional delete button is a **sibling** of the selectable `<button>`, not nested inside it (a `<button>` inside a `<button>` is invalid HTML and breaks keyboard/screen-reader navigation), positioned on top of the card's corner with CSS instead.

`postavy.ts` is the one place the five characters (Kael, Lyra, Rayen, Elara, Drakon — the roster was swapped wholesale to a second art generation partway through the game hub's build; see below) live, and since the card/combat system below now exists, their bonuses are real numbers on `Postava` (`bojZivel`, `bojNasobicPoskozeni`, `bojKriticka`, `bojKritickyNasobic`, `bojVydrz`) feeding actual combat math, not just descriptive card text any more.

**Character art is a real portrait, not just an emoji badge.** `Postava.portret` points at `public/postavy/<id>.jpg` — a 280×764 px crop taken directly out of the reference sheet's own per-hero card, cropped with the same Pillow-and-JPEG pipeline as the world map (`public/backgrounds/`), and excluded from install precache the same way (a `CacheFirst` runtime-caching rule in `vite.config.ts` keyed on `/postavy/`, fetched lazily the first time `/hra` opens, `/hra` being a route most users don't visit). The source crop already bakes in the hero's name, title, element and role as part of the illustration — `PostavaKarta.tsx` renders it as-is rather than re-typesetting that text, and only overlays what the image can't know: the small `ikona` emoji badge (the same compact marker used everywhere *outside* the card — map top bar, Souboj, Obchod, Hrdina — kept as a separate field from `portret` for exactly that reason), a level badge, the selection checkmark, and the mechanical bonus/nevýhoda list below it. `PostavaKarta`'s `alt` text repeats the name and subtitle for screen readers, since that information only exists as pixels otherwise. `POSTAVA_IDS` in `core/utils/gameCharacterValidation.ts` moved to the new ids in the same swap — same accepted tradeoff as the map's location-id rewrite: `jePlatneId`'s item-by-item filtering means a save with the old ids just silently loses those characters (and their level progress) rather than crashing, nobody wrote a migration for it.

**Selecting a character is a horizontally-scrolling, scroll-snapping carousel, not a vertical list.** `TvorbaPostavy.css`/`VyberPostavy.css`'s `.tp-mrizka`/`.vp-mrizka` are `flex-direction: row` with `overflow-x: auto` and `scroll-snap-type: x mandatory`; each `.postava-karta-wrap` (and the "add another" tile in `VyberPostavy`) is `scroll-snap-align: center` at a fixed `min(78vw, 260px)` width — one card mostly fills a phone screen with the next one peeking at the edge, the natural width for a 280×764 portrait crop displayed near its native size. Scrolling and selecting stay two separate actions on purpose, same as the pre-carousel grid: swiping just moves which cards are in view, tapping one toggles `is-vybrana`, and only the fixed bottom bar's button (`tp-pokracovat`/`vp-hrat`, unchanged) commits the choice — so browsing a few cards sideways before deciding never accidentally creates or picks a character.

**The in-game shop (`src/game/obchod/`, opened from the Tržiště pin) sells permanent, account-wide upgrades, not consumables.** `PREDMETY` is a flat list (one market exists today; a second with a different selection would become a location-keyed map, same shape as `nepratele.ts`) bought with the same combat credits `useWalletStore` already tracks, and ownership reuses that store's existing `ownedItems`/`grantItem`/`ownsItem` exactly as the cosmetic Shop does — no new persisted state. Deliberately account-wide rather than per-character, on purpose and unlike leveling below: an upgrade benefits whichever character you're playing when you buy it *and* every character afterward — a shop purchase is a decision about the account's wallet, not earned progress tied to one save slot, so it doesn't follow leveling into per-character storage even though per-character storage exists now. `useSouboj.ts` reads `ownedItems` directly and folds the bonuses into the fight — extra max HP, a flat damage multiplier applied before the character's own element-match bonus (so it's honestly "+10% on every card," not just the character's favoured element), and an added crit chance, stacked with that character's own level/skill bonuses (see leveling below) into one combined number. **`obchodNasobicCeny` (a 20 %-pricier downside, carried by Lyra since the roster swap — Angel had it before her) finally has a consumer**: every price in the shop is `Math.round(cena * postava.obchodNasobicCeny)`, so shopping as Lyra costs visibly more for the exact same upgrade — the shop screen surfaces that as its own line ("Jako Lyra platíš o 20 % víc", built from `postava.jmeno` so it needed no change when the downside moved to a different hero) rather than leaving the markup silent in the numbers.

**The card/combat system (`src/game/combat/`) is a small, self-contained turn-based battle, deliberately not a deckbuilder.** `karty.ts` holds one shared card pool, two cards per element, that every character can play — a character's bonus only multiplies damage for cards matching their own `bojZivel`, it doesn't restrict which cards they draw. The pool grew from 5 elements/10 cards to 7/14 with the hero-roster swap above: Lyra's Arcane and Drakon's Dark didn't honestly map onto any of the original `svetlo`/`ohen`/`vzduch`/`zeme`/`voda`, so `Zivel` gained `arkana`/`tma` (two new cards each) rather than forcing a lossy remap. `zeme`'s own two cards got renamed in the same pass — Elara's element is Nature, not rock, so "Kamenná pěst"/"Zemětřes" became "Trnitý spár"/"Kořenový úder" (ids unchanged, only `nazev`/`ikona`) and `NAZEV_ZIVLU.zeme` became "Příroda". `svetlo` and `vzduch` now have no character granting their bonus — the new five only span 4 of the (now 7) elements plus the two new ones — but the cards stay in the pool; anyone can still play them, they just don't get a damage bonus from any current hero. `useSouboj.ts` is a plain hook holding ephemeral React state (no persistence, no Zustand store — leaving mid-fight via the back button costs nothing): each round deals a 3-card hand off a shuffled deck (see Fáze 5 below), playing a card rolls damage in its range, applies the element-match multiplier and a per-character crit chance/multiplier, then the enemy immediately counter-attacks, until either side hits zero. A win pays out through the existing systems rather than inventing new ones: `recordAction('battle', xp)` (a new `ActivityKind`, with its own count-based badge `arena_champion`) and `useWalletStore().credit()` for the credits — guarded by a ref so retrying a fight only pays out on an actual new win, not on every re-render of the win screen.

**Every character also carries a `specialniSchopnost` (Fáze 4, combat system) — one signature move, usable once per fight, outside the card pool entirely.** It's the one piece of real tactical choice this combat system had been missing: until now "which of three random cards" was the only decision a fight ever asked for. Three effect shapes cover all five heroes today (`TypSchopnosti`: `'poskozeni'`/`'leceni'`/`'stit'`) — deliberately not a general status-effect engine, because nothing yet needs a fourth shape; one gets added only once an actual ability needs it, not speculatively. Kael's is a `'stit'` (blocks the next counter-attack outright), Elara's a `'leceni'` (heals), Lyra/Rayen/Drakon are `'poskozeni'` (guaranteed damage, no card RNG) — Drakon's alone carries `vlastniNaklad`, self-damage that makes his the one genuinely risky pick, matching his "destroys everything in his way" reference-sheet flavor. `useSouboj.ts` was refactored so both `zahratKartu` and the new `pouzitSchopnost` resolve through one shared `vyhodnotAkci` — enemy-defeated/next-enemy/counter-attack logic used to live only inside `zahratKartu`, and copy-pasting it for the ability would have meant two places that could silently drift (a dungeon transition fixed in one and not the other, for instance). `SoubojStav.schopnostPouzita` doesn't reset between enemies in a dungeon — one signature move for the whole run, not one per enemy — only `zkusitZnovu` (a fresh attempt) clears it. `Hrdina.tsx`'s Statistiky-adjacent "Schopnost" card is purely informational (the ability only *does* anything inside `Souboj.tsx`) but keeps that screen's own promise — everything about the character you're playing, not scattered across screens.

**Fáze 5 (cards) fixed the hand actually being a hand, not fourteen independent coin flips every turn.** The old `nahodnaRuka` drew each of the 3 cards from the *entire* pool independently, so nothing stopped the exact same card turning up in four hands running — `useSouboj.ts` now deals from a real shuffled deck (`zamichanyBalicek`, Fisher–Yates) via `dalsiRuka`, which slices 3 off the front and only reshuffles a fresh copy once fewer than 3 remain — no card repeats until the whole 14-card pool has been seen once. `vyhodnotAkci`'s three branches that deal a new hand (win-and-continue, shield-block, ordinary turn) all thread `s.balicek` through the same `dalsiRuka` call, so the deck state never drifts between the card-path and the ability-path. Three of the fourteen cards also gained a secondary effect, `vlastniLeceni` — a flat self-heal on top of damage, reusing `VysledekAkce.zmenaVlastniVydrze` from the Fáze 4 refactor rather than inventing a second effect channel. Deliberately only the strong variant of the three "supportive" elements (Zář/light, Příliv/water, Kořenový úder/nature) — fire/wind/arcane/dark stay purely offensive, an intentional split in element character, not an oversight to fix later. `Souboj.tsx` shows a small "💚+N" badge on any card carrying it, so the choice is visible before playing, not a surprise in the log.

**Lyra's special ability was renamed from "Arkánní výboj" to "Arkánní příval" during this phase** — that exact name already belonged to the strong arkana *card* (`karty.ts`), and having both the ability button and a card in hand read "Arkánní výboj" with different effects on the same screen was a real, confusing collision caught while extending this same file, not a hypothetical one.

**`nepratele.ts` maps a location id to `Nepritel[]`, not a single enemy — the same "add a record, don't touch the renderer" shape as `lokace.ts`.** The Arena is a one-element array; a dungeon is several fought back to back by `useSouboj`, and **the player's HP is deliberately never restored between them** — only a fresh "Zkusit znovu" resets it. That's what makes a dungeon a harder, distinct kind of content rather than "the Arena with a different name": three easy fights in a row with no healing is a real endurance test even though each individual enemy is weak. Rewards accumulate across the whole run and pay out once, at the end, together — losing partway through a dungeon forfeits the XP/credits already "earned" from the enemies beaten so far, same as losing the Arena's one fight forfeits that fight's reward. `Souboj.tsx` shows a "Soupeř *n* / *total*" pill only when there's more than one enemy, so the Arena's single-fight screen stays exactly as uncluttered as before. The next combat location is still just one entry in `nepratele.ts` plus its own enemy data — no `MapaSveta.tsx`/`Souboj.tsx` change needed.

**Fáze 6 (inventory) added loot as a system deliberately separate from the shop's `Predmet`/`ownedItems` (`src/game/obchod/`), not a reuse of it.** The shop sells permanent, once-owned, account-wide upgrades (`useWalletStore.ownedItems`, a set of ids you either have or don't); loot is spendable and countable — you can hold several potions and use them up one at a time. Sharing one type/store between the two would have made "own a permanent blade upgrade" and "carry three potions" the same shape when they aren't, so loot gets its own type (`Lup`, `game/data/items.ts`), its own store (`useInventarStore.ts`, `predmety: Record<lupId, count>`), and its own validation (`inventarValidation.ts`, registered in `BACKUP_STORES`). `Nepritel` gained optional `lupId`/`sanceNaLup` — a drop chance rolled once per defeated enemy inside `vyhodnotAkci` (a pure function, no store write there) via `vyhodnotLup`; `Souboj.tsx`'s existing win effect (already granting XP/credits/quest completion exactly once per real win) is where the roll actually lands in the store, via `pridatPredmet`.

**Using an item in combat is the third action type through `vyhodnotAkci`, proving out the extensibility the Fáze 4 refactor was built for.** `pouzitPredmet(lupId)` sits next to `zahratKartu`/`pouzitSchopnost`: it spends one unit from `useInventarStore` immediately (via `spotrebovatPredmet`, which returns whether the player actually had one — a no-op if not), then resolves its effect through the same `vyhodnotAkci` pipeline as everything else, so an item still costs the turn and the enemy still counters afterward exactly like a card or ability would. Unlike `specialniSchopnost`, it isn't capped at once per fight — only by how many units are actually in the bag, which `Souboj.tsx` reads live from `useInventarStore` to decide whether the item row renders at all (nothing to show once the count hits zero). `Inventar.tsx` is the read-only counterpart — opened from the map's floating menu, the third `.mapa-menu-dlazdice` tile — for browsing what's in the bag outside of combat, the same "browse here, act in `Souboj.tsx`" split `Questy.tsx`/`MapaSveta.tsx` already established for quest objectives.

**The world map is one illustrated bitmap (`public/backgrounds/mapa-sveta.jpg`, "Buddy Realm") with pins laid over it, not a procedurally-drawn SVG scene.** An earlier version of this map drew the terrain, trunk path, river and branch spurs itself — mlhoviny (glow blobs), contour rings, a grid pattern, a gold→violet→teal gradient path with a `feGaussianBlur` glow layer underneath an animated `stroke-dashoffset` layer on top, carefully split exactly that way after a measured jank problem (animating a *filtered* SVG element forces the browser to re-run the blur every frame instead of compositing a cached bitmap; under 4× CPU throttling that alone dropped real frames, measured with a scripted scroll loop sampling `requestAnimationFrame` deltas, not eyeballed). That whole layer is gone now, replaced with the user's own illustrated map — a single static `<img className="mapa-obrazek">` costs the browser a normal image decode once, nothing to recompute per frame, which makes the entire earlier "split static-filtered-layer from animated-unfiltered-layer" exercise moot rather than something to keep maintaining. `lokace.ts` holds a hand-placed list of locations (`{x, y}` as percentages of the image's own pixel dimensions, read off the actual illustration — Frostheim, Voidspire, Solace as capital, etc. — not derived from any formula, so swapping the artwork means re-reading every coordinate by eye, not recalculating one) and no longer distinguishes "trunk" from "branch" locations (`vedlejsi`/`Vetev`/`VETVE` are gone) — the old distinction existed only to justify which procedural path segment a location sat on, and this map doesn't have procedural path segments any more, just labelled cities sitting where the artist put them.

`SVET_SIRKA_PX`/`SVET_VYSKA_PX` in `MapaSveta.tsx` must match the CSS `.mapa-svet` width/height *and* the actual pixel dimensions of `mapa-sveta.jpg` — three places now instead of the old map's two, because pin percentages are meaningless without knowing the exact bitmap they were read against. The map opens centered on the capital (Solace) on **both** axes now (the old map only centered horizontally, since it was a vertical trunk with sideways branches; this one is a real 2D world, so centering needs both `scrollLeft` and `scrollTop`). `mapa-sveta.jpg` is deliberately excluded from the PWA install precache the same way `mediapipe/**` is (see **Form Check** below) — `.jpg` isn't even in the `globPatterns` extension list, and a dedicated `CacheFirst` runtime-caching rule in `vite.config.ts` fetches it lazily the first time `/hra` actually opens, then serves it from cache offline after; nobody who never plays the game should pay ~400 KB at install time for an image they'll never see.

Tapping a pin opens a bottom sheet — that part is unchanged from before. The capital still gets a bigger pin with its own breathing halo (a `::before` animating only `opacity`/`transform`, compositor-only, cheap regardless of what's under it) and a distinct message ("vyhrazené pro dějovou linku, ta zatím nevznikla") from every other content-less location's generic "zatím nikam nevede". A location with a defined enemy (`combat/nepratele.ts`) still gets its own sheet copy and a "Vstoupit do boje" button — `MapaSveta` just checks whether `NEPRATELE_PODLE_LOKACE[lokace.id]` exists, so the next combat location is still only a data entry, no branch added here. The two ids that already carry real fight content (`arena-krvavy-kruh`, `dungeon-stinne-jeskyne`) kept their exact ids across the rewrite even though their in-game names/positions changed ("Aréna Solace", "Molten Core") — renaming the id instead of just the label would have silently orphaned the fight data with no type error to catch it.

**`App.tsx` still imports `GameModule` through `React.lazy`**, left over from when the route carried Three.js. For a while after the map/character rebuild `/hra` imported no `three` at all — only `/social` did — so the two routes shared neither a dependency nor a bundle chunk. The 3D exploration mode below brought `three` back into `/hra`, exactly the "a future stage may well bring real weight back" this paragraph used to flag; Vite responded exactly as CLAUDE.md predicted it would, deduping `three` into its own shared chunk the moment a second route imported it, no config change needed.

### 3D exploration — the map → world → combat → quest loop (`src/game/explorace/`, `src/game/data/`)

**A location on the map can now open a real 3D first-person world instead of only a bottom-sheet blurb, and walking into what's waiting there is what starts the fight — not a button in the sheet.** This is the first "location with actual content" the map's generic locations were always waiting for (see the "zatím nikam nevede" placeholder text above): `lokace.ts` gained a fourth `LokaceTyp`, `'explorace'`, and `MapaSveta.tsx` initially checked it the exact same way it already checked `NEPRATELE_PODLE_LOKACE` for a direct-to-combat location — a lookup against a new `SVETY_PODLE_LOKACE` map (`game/data/world.ts`), no new branch shape, just a different data table and a different sheet button ("🌲 Vstoupit do světa" instead of "⚔️ Vstoupit do boje"). `Emberfall` was the one location wired up at first, holding Season 1's first quest, "Ztracené štěně" (The Lost Pup) — the other 6 planned locations and 29 planned side quests are still deliberately not stubbed out; adding one is "a new `Lokace` + a new `SvetKonfigurace` + a new `Nepritel[]` entry + a new `Quest`," the same low-ceremony shape every other content table in this file already has, not a new system. (See **Fáze 7 (dungeons)** below for why that `typ === 'explorace'` check was later replaced with a presence check against `SVETY_PODLE_LOKACE` instead.)

**The loop is Map → Location → 3D world → exploration → encounter → the *existing* 2D card combat → reward → quest complete → XP → back to the map — deliberately not a 3D combat system.** `Explorace3D.tsx` (the screen) and `usePlayerWorld.ts` (the engine, see below) know nothing about cards, decks, or damage math; the only thing exploration produces is one event, "the player reached the monster," surfaced as `onSetkani`. `GameModule.tsx` reacts to it by setting the *same* `soubojLokaceId` state a direct arena/dungeon pin already sets, so from that point on it's the same `Souboj.tsx`/`useSouboj.ts` that every other fight in the game already uses — `combat/nepratele.ts` gained one more entry (`emberfall`, a Stínovlčák) rather than exploration growing a parallel enemy/reward system. Leaving the fight (win or lose) clears both `soubojLokaceId` *and* `exploraceLokaceId` in one place, so the player lands back on the map, never back inside the 3D world they just left.

**Quest completion is a new, deliberately tiny store (`useQuestStore.ts`), not a field bolted onto `useGameCharacter` or the gamification store.** A quest is account-wide progress like badges (finishing it isn't tied to which character happens to be selected this session), but it isn't XP/streak/badge data either, so it doesn't belong in `useGamificationStore` — its own `secureStorage`-backed persist, validated the same item-by-item way as `gameCharacterValidation.ts` (`questValidation.ts`, deriving valid quest/objective ids straight from `QUESTS` instead of keeping a second hardcoded id list that could drift out of sync). Registered in `BACKUP_STORES` like every other persisted key must be. `Souboj.tsx` still doesn't know quests exist: it grew one optional prop, `onVyhra`, called once alongside the existing `recordAction`/`credit`/`pridatXpPostave` effect on a real win, and only `GameModule.tsx` decides — via `BOJOVY_CIL_PODLE_LOKACE`, `game/data/quests.ts` — whether that fight happens to be the one that finishes a quest objective. A location with combat but no quest attached (the Arena, the existing dungeon) simply never passes `onVyhra`.

**A quest has an explicit life cycle — `nedostupny` → `aktivni` → `splneny` — and a list of `cile` (objectives), not one flat `cil` string and an implicit "walking in is accepting."** The vertical slice's `Souboj`-only wiring worked for exactly one quest with exactly one step; a real quest engine has to support quests that need more than one thing done, possibly of different kinds (`TypCile` is `'boj'` today, on purpose the only case built so far — a dialogue or item-collection quest later adds a new value here, not a new store). `MapaSveta.tsx`'s location sheet now gates on this: an `'explorace'` location with an unaccepted quest shows "📜 Přijmout quest" instead of the world-entry button, and only after `prijmoutQuest()` does the sheet switch to a checklist of `cile` plus "🌲 Vstoupit do světa." `BOJOVY_CIL_PODLE_LOKACE` maps a location to *which* quest and *which one objective* a win there satisfies (`{ questId, cilId }`, not just a quest id) — a quest whose objectives span more than one location, which will exist soon, couldn't be expressed by a flatter mapping. `useQuestStore.splnitCil(questId, cilId)` marks that one objective done and only promotes the quest into `dokoncene` once every objective in `Quest.cile` is done, computed against the quest's own data, not a hand-maintained counter.

**`Questy.tsx` is the quest log, opened from the map's floating menu — the second `.mapa-menu-dlazdice` tile, proving out the "adding a feature is one more tile" claim made when that menu shipped with only Hrdina in it.** Three sections (Aktivní/Dostupné/Splněné), each just `QUESTS.filter(...)` against the store's `aktivni`/`dokoncene` arrays — a "Dostupné" quest (visible on the map, not yet accepted) is deliberately listed here too, not hidden until accepted, so a player can see what's out there before committing to it.

**`stavQuestu`/`jeCilSplneny` are plain exported functions taking the store's raw arrays as arguments, not methods living on the store itself — a real bug this phase hit and fixed, not just a style choice.** The first version put them on the store (`stavQuestu: (id) => { ... get() ... }`), and every consumer subscribed to `useQuestStore((s) => s.stavQuestu)`. That never re-rendered after `prijmoutQuest()`: Zustand only re-renders a component when the *selected value* changes by `Object.is`, and a method defined once in the store creator is the same function reference for the store's entire lifetime — the underlying `aktivni`/`dokoncene` arrays it reads via `get()` had genuinely changed, but the selected value (the function itself) hadn't, so nothing told React to re-render. The sheet was stuck showing "Přijmout quest" forever, caught by the e2e test asserting the checklist actually appears after clicking it — the same category of mistake `leveling.ts`'s pure-function pattern already avoided elsewhere in this file, now enforced here too: compute derived state in the component (or a pure helper it calls) from data the component actually subscribes to, never from a store method that closes over `get()`.

**Story (Fáze 3) is a small dialogue-sequence engine, not text hand-written inside the components that happen to trigger it.** `game/data/story.ts` holds `STORY: Record<string, DialogSekvence>` — ordered `DialogRadek[]` (speaker, icon, text) keyed by an id — and `Quest` (`data/quests.ts`) gained two optional fields, `dialogPriPrijeti`/`dialogPriDokonceni`, that just name a sequence to play. `StoryDialog.tsx` is the one player: full-screen (not a translucent overlay — a short scene, matching how a visual novel dialogue box works, not a sheet over something else), one line at a time, tap-anywhere or the "Dál ▸" button to advance, "Přeskočit" to bail out early, a dot-per-line progress indicator at the top. It's reused as-is in two different places in the loop — `MapaSveta.tsx` renders it inline right after `prijmoutQuest()` (the accept beat, still on the map), `GameModule.tsx` renders it as its own screen tier after a win that completed a quest (the payoff beat, between combat and the map — literally the "Story" step in this feature's own loop diagram, Souboj → reward → quest complete → XP → **Story** → map). Neither caller hardcodes who's talking: a line's `mluvci` can be a literal NPC name from the data, or the sentinel `'__hrac__'`/`'__buddy__'`, which `StoryDialog` resolves at render time to the actually-selected `postava.jmeno`/`.ikona` (data has no way to know which of the five heroes is being played) or to a fixed Buddy identity — the same reasoning as `Postava.ikona` being resolved per-character everywhere else in this file.

**`useQuestStore.splnitCil` returns `true` only on the call that actually finished the quest, not on every partial objective — that boolean is what gates the completion dialogue.** Without it, a multi-objective quest would replay its epilogue after each objective, and `Souboj.tsx`'s `onVyhra` — which fires on every win at a quest-linked location, including a player re-fighting an already-cleared encounter — would replay it forever. `GameModule.tsx` only calls `setStoryId(...)` when `splnitCil(...)` returns `true`, so the dialogue plays exactly once, the moment the quest's last objective clears.

**`usePlayerWorld.ts` is plain Three.js, not React Three Fiber — matching this codebase's existing pattern instead of introducing a second one.** Social's ambient scene and Form Check's pose engine already both own a renderer/camera/render-loop entirely outside React (`useAmbientScene.ts`, `usePoseEngine.ts`) and clean it up on unmount; the exploration hook is a third instance of that exact shape, not a different paradigm bolted on next to it. It builds the world from plain geometry — a ground plane, cone-and-cylinder "trees," dodecahedron "rocks," an icosahedron enemy with a point light and a slowly-turning halo torus, and a two-sphere "core + glow" Buddy companion lifted straight from `useAmbientScene.ts`'s koule technique — because there is no real 3D asset pipeline in this project and downloading one from a third-party source would break the "runs completely without the cloud, self-hosted assets only" rule that already governs Form Check's models and the map/character art. Fog (`scene.fog`, colour from `SvetKonfigurace.barvaMlhy`) does double duty as both atmosphere and a cheap draw-distance cutoff.

**Input is unified through the Pointer Events API so the same code drives mouse-drag-to-look on desktop and touch-drag-to-look on mobile** — a pointerdown/pointermove/pointerup triplet on the canvas container updates yaw/pitch directly, clamped so the player can't flip past vertical. Movement is separate: WASD/arrow keys on desktop, or `VirtualniJoystick.tsx` on mobile — a small DOM control living *outside* the canvas container's own DOM subtree, which is what makes a touch on the joystick never also register as a look-drag (the browser dispatches a pointer event to whichever element is actually under it; a sibling element with its own listener simply never sees a touch that landed on the joystick). The joystick hides itself under `@media (pointer: fine)` rather than a JS device check, so a touchscreen laptop still gets it while a mouse-only desktop doesn't have it sitting uselessly in the corner. The player's starting facing direction is computed from `SvetKonfigurace.start`/`poziceSetkani` (`Math.atan2`), not hardcoded — a location where the encounter isn't roughly "in front of" the spawn point would otherwise start the player facing away from the only thing there is to walk toward.

**`Explorace3D` is lazy-loaded from `GameModule.tsx` (`React.lazy`, `Suspense` with a shared `.game-lazy-fallback`), the same reasoning as `SocialModule`/`GameModule` itself in `App.tsx`:** the three.js weight should be paid only by a player who actually opens an `'explorace'` location, not by everyone who visits `/hra`. Unlike the map image and character portraits (lazily *fetched* — real bytes over the network, cached after), this is lazily *bundled* — a separate JS chunk Vite only requests when the dynamic `import()` actually runs.

**Fáze 7 (dungeons) gave the existing dungeon (`dungeon-stinne-jeskyne`, "Molten Core," `typ: 'dungeon'`) the same 3D entrance Emberfall has, without turning it into an `'explorace'` location.** The dungeon already had real content before any of this — three sequential enemies in `combat/nepratele.ts` with HP that deliberately never restores between them (see the dungeon paragraph under **Game hub** above) — it just still opened straight into `Souboj.tsx` from the map sheet, the pre-3D flow every combat pin used before Emberfall's vertical slice. Relabelling it to `typ: 'explorace'` would have worked but would have also renamed its display type from "Dungeon" to "Průzkum" on the map sheet for no real reason — the type describes *what the place is*, not *whether it happens to have a 3D entrance*, and those turned out to be independent questions the first time a second location needed 3D. So `MapaSveta.tsx`'s `jeExplorace` flag changed from `detail?.typ === 'explorace'` to `!!SVETY_PODLE_LOKACE[detail?.id ?? '']` — a data-presence check, same shape as the pre-existing `NEPRATELE_PODLE_LOKACE` lookup right next to it — and the dungeon kept its own `typ`/label/colour while gaining "🌲 Vstoupit do světa." `world.ts` gained a `'jeskyne'` (cave) `TerenTyp` alongside `'pole'`/`'les'`: `usePlayerWorld.ts`'s decoration loop now forces cave terrain to place only rocks, never trees (a `DodecahedronGeometry` scatter, no `jeStrom` roll), and the cave's `SvetKonfigurace` uses a smaller `polomerSveta` (16 vs. Emberfall's 26) and near-black sky/fog/ground colours for a deliberately claustrophobic feel instead of another open field with a different palette.

**The dungeon has no quest attached (same as before this phase — see the dungeon paragraph under Game hub), so its 3D entrance needed its own HUD, not the quest banner Emberfall shows.** `Explorace3D.tsx`'s HUD block only ever handled the quest case; a location with `NEPRATELE_PODLE_LOKACE` entries but no `QUESTS` entry would have shown nothing at all walking in, which reads as a bug on a screen that already has a HUD pattern established. It now also checks `NEPRATELE_PODLE_LOKACE[lokace.id]` when there's no quest, and shows a distinctly-styled warning (`.explorace-quest-hud--varovani`, red instead of the quest banner's gold) naming the enemy count and the no-healing rule up front, before the player commits to walking further in. `MapaSveta.tsx`'s sheet text got the same nepratele-aware branch inside the `jeExplorace` case, for the same reason — the sheet already distinguished a single-enemy fight from a multi-enemy one for direct-combat locations (`nepratele.length > 1`), and a 3D-entrance location deserves the same distinction instead of a generic "new place to explore" line that would undersell what's actually waiting inside.

The loop itself needed no changes: `GameModule.tsx` already treats every `'explorace'`-flagged 3D world identically regardless of what's on the other side of the encounter (see the loop paragraph above) — the dungeon's `onSetkani` sets the same `soubojLokaceId` state Emberfall's does, and from there it's the pre-existing multi-enemy `Souboj.tsx`/`useSouboj.ts` flow, unmodified, that already shows the "Soupeř *n* / *total*" pill and carries HP across all three fights. Proving the loop generalizes to a second, quest-less, multi-enemy location without touching `GameModule.tsx`'s screen-tier logic at all is exactly what this phase set out to show.

**Fáze 8 (bossové) turned the dungeon's existing final enemy, "Strážce jeskyně" (already the strongest of its three, already literally named "Guardian"), into a real boss — not a new content system, three optional fields on the existing `Nepritel` (`jeBoss`, `zuriPodHp`, `zuriNasobicPoskozeni` in `combat/types.ts`).** A location doesn't need a new `Lokace`/`SvetKonfigurace`/quest to get a boss; any entry in `NEPRATELE_PODLE_LOKACE` can become one by adding those three fields, the same low-ceremony shape as everything else in that file. The Arena's and Emberfall's enemies stay plain — a boss is something a fight *can* have, not something every fight needs.

**The one real mechanic a boss adds is an enrage phase, resolved entirely inside the existing shared `vyhodnotAkci` pipeline (Fáze 4) rather than a parallel combat path.** Once a boss's HP crosses `zuriPodHp` (a fraction of its max, e.g. 0.4), `zuriTeto` — a value computed fresh on every `vyhodnotAkci` call — turns permanently true for the rest of that specific fight (carried forward via `SoubojStav.nepritelZuri`, reset to `false` when the fight moves to the next enemy in a dungeon or restarts via `zkusitZnovu`) and its counter-attack damage is multiplied by `zuriNasobicPoskozeni` from that point on. This is deliberately a one-way, single-condition switch — not a general status-effect/phase engine — because nothing yet needs more than "the boss hits harder once badly hurt," the same restraint already applied to `specialniSchopnost`'s three effect shapes when a fourth wasn't yet needed. The transition logs its own line (`"😡 {jméno} se rozzuřil!"`) exactly once, the turn it happens, computed via a `zuriPoprve` flag (`zuriTeto && !s.nepritelZuri`) so the message can't repeat on every subsequent turn the boss stays enraged.

**A boss's badge and win screen are additive reads of `Nepritel.jeBoss`, not a second reward system running alongside the existing one.** `Souboj.tsx`'s win effect still calls `recordAction('battle', odmenaXp)` exactly as before for the XP/credits/counter — a boss fight *is* a battle — and only adds one extra call, `recordAction('boss', 0)`, when the just-defeated enemy (still readable off `nepritel` at the moment `faze` becomes `'vyhra'`, since `indexNepritele` isn't advanced on the final kill) has `jeBoss` set; the `0` XP argument is deliberate, the real XP was already awarded by the `'battle'` call on the line above, this call exists only to bump the `'boss'` counter and let `COUNT_BADGES` unlock `boss_slayer` at `needed: 1`. `ActivityKind` gained `'boss'` alongside `'battle'` for exactly that — the counter/badge pairing pattern already established for every other `ActivityKind`, not a bespoke one-off `unlockBadge` call. The win screen swaps its trophy for a crown and its heading for "Boss poražen!" when `nepritel.jeBoss` is true (checked before the existing dungeon-vs-arena heading logic, since a boss fight finishing a dungeon deserves the more specific message); mid-fight, the enemy card gets a "👑 BOSS" pill and, once enraged, a pulsing red glow and "😡 Rozzuřen" tag (`.souboj-bojovnik--zuri`, an `@keyframes` alternating box-shadow colour, disabled under `prefers-reduced-motion` like every other looping animation in this file) — all of it reading `nepritelZuri`, which `useSouboj` now exposes alongside the rest of its state. The sheet text and 3D-entrance warning HUD from Fáze 7 (both already nepratele-aware for the dungeon's quest-less multi-enemy case) gained one more conditional line — "Na konci čeká boss." — when any enemy in that location's array carries `jeBoss`, so a player commits to the dungeon already knowing what's actually waiting at the end.

**Fáze 9 (character progression) added equipment — `Vybaveni` (`game/data/equipment.ts`), a deliberately third mechanic next to the shop's permanent `Predmet` and the inventory's consumable `Lup`, not a reuse of either.** The shop's `ownedItems` is boolean and account-wide with no choice involved (own it, it's always active); loot is consumed the instant it's used. Equipment is owned once (like the shop) but *equipped per character* (like level/skill points in `leveling.ts`) and can be swapped or removed at will — none of the three existing shapes fit, so it gets its own store, `useVybaveniStore.ts`, with two separately-shaped fields: `vlastnene: string[]` (account-wide ownership, same shape as `ownedItems`) and `nasazene: Record<postavaId, vybaveniId>` (which character has what equipped, mirroring `useGameCharacter.progres`'s per-character keying). Registered in `BACKUP_STORES` and validated the same item-by-item way as every other store this session added (`vybaveniValidation.ts`, ids derived from `VYBAVENI` and postava ids from the existing `POSTAVA_IDS` in `gameCharacterValidation.ts` rather than a third copy of that list).

**Equipment drops are guaranteed, not rolled — the opposite design choice from batohový loot on purpose.** `Nepritel` gained `vybaveniId` (`combat/types.ts`) alongside the existing `lupId`/`sanceNaLup`: a boss's signature relic is always awarded on the win that defeats it (`Souboj.tsx`'s win effect calls `ziskatVybaveni` unconditionally when the field is present, no `Math.random()` involved, and the store's own `ziskatVybaveni` is idempotent so refighting an already-cleared boss can't grant duplicates), while a potion drop is still a chance. A boss fight is a one-shot, deliberately memorable moment — a coin-flip on whether it pays out its whole point would undercut that in a way a common enemy's potion chance doesn't. The win screen's existing loot line (Fáze 6) gained a sibling paragraph for this, pointing the player at the Hrdina screen to actually equip what they just earned.

**The equip bonus feeds into the exact same `vypocitejBojoveStatistiky` every other combat number already goes through, not a fourth parallel calculation.** The function gained one more optional argument (`nasazenaVybaveniId`) alongside `ownedItems`, folding the equipped item's `bonusVydrz`/`bonusPoskozeni`/`bonusKriticka` into the same three-source sum the doc comment above it already described (shop + level/skills, now + equipment) — both call sites (`useSouboj.ts`'s hook, which reads `useVybaveniStore.nasazene[postava.id]` itself, and `Hrdina.tsx`'s Statistiky section) pass it the same way, so an equipped relic can never show one number on the character card and a different one in an actual fight. `Hrdina.tsx` gained a "Vybavení" section between Vylepšení and the skill tree, reusing the skill tree's own `.hr-uzel`/`.hr-vylepsit` markup rather than inventing new card styling — a plain equip/unequip toggle per owned piece, with an empty-state hint pointing at bosses when nothing's owned yet. Only one relic exists today (Amulet strážce, from the dungeon's Strážce jeskyně) — the next one is, as with every other content table in this file, one more `Vybaveni` entry plus a `vybaveniId` on whichever future boss drops it.

**Fáze 10 (Season 1 content) is being built incrementally rather than in one pass — 7 locations, 30 side quests and 5 named bosses is real scope, not a single unit of work.** The actual illustrated map (`mapa-sveta.jpg`) already names its regions — Frosthold, Shadowveil, Elenwood ("The Eternal Forest," Greenhaven's own subtitle), Emberwaste, Dawnbreak Fields, Sandcrown, Verdant Vale — and those don't line up one-to-one with the original spec's location list (there's no separate "Old Forest" pin distinct from Greenhaven's forest on the actual art; a second pin for the same patch of trees would look wrong on the illustration). Rather than inventing pins the art doesn't support, each Season 1 story beat attaches to whichever existing city pin already carries the matching region theme — Greenhaven *is* "Old Forest" here, its 3D world representing the Eternal Forest surrounding the town, the same "the world is the land around the town, not the town itself" relationship Emberfall's fields already established to Emberfall.

**Greenhaven, Voidspire and Frostheim all keep their existing `typ: 'mesto'` on the map — this is the decoupling from Fáze 7 (dungeon) proving out on three differently-typed locations, not a one-off special case.** `MapaSveta.tsx`'s `jeExplorace` already reads `SVETY_PODLE_LOKACE` presence, not `Lokace.typ`, so giving any of these cities a 3D world needed *zero* code changes in `MapaSveta.tsx`, `Explorace3D.tsx`, `GameModule.tsx` or `useSouboj.ts` — only data, each time the same four-file recipe: a `SvetKonfigurace` in `world.ts` (Greenhaven's dark forest palette, Voidspire's corrupted-violet plain, Frostheim's icy navy — the latter two both reuse `teren: 'pole'`/`'jeskyne'` from earlier locations with an entirely different palette, proving terrain type and colour palette are independent knobs, not one setting), one quest in `quests.ts` (each a single `'boj'` objective — deliberately not yet the multi-location multi-objective shape the quest engine's comments already flagged as coming "soon," saved for a location that actually needs it rather than forced here for its own sake), two `STORY` sequences per quest, and one boss-only `Nepritel` entry (Strážce lesa at Greenhaven, Stínová královna at Voidspire, Zamrzlý strážce at Frostheim — the spec's "Forest Guardian," "Shadow Queen" and "Frozen Guardian" — each a single `'explorace'` encounter shaped like Emberfall's, not a `dungeon`-style multi-enemy chain).

**Four relics now exist, and they were deliberately built to spread across four different archetypes rather than four flavours of the same stat.** Amulet strážce (dungeon) is balanced-defensive (`bonusVydrz`/`bonusKriticka` together), Trnová koruna (Greenhaven) leans offensive (`bonusPoskozeni`), Stínový plášť (Voidspire) leans risky (`bonusKriticka` dominant, little else), Ledový štít (Frostheim) is pure tank (`bonusVydrz` alone, nothing else) — with only `useVybaveniStore`'s single equip slot, relics that actually pull in different directions is what turns "which one is equipped" into a real build choice instead of "whichever was found most recently."

**Each story location's `dialogPriDokonceni` line references the ones before it, turning independent side content into a felt through-line without any code coordinating it.** Emberfall's ending hints at something waking up beyond the town; Greenhaven's guard explicitly says "Napřed Emberfall, teď Věčný les"; Voidspire's guard goes one further — "Emberfall, Greenhaven, teď my... kdosi budí staré strážce jednoho po druhém"; Frostheim's guard closes the loop so far — "Emberfall, Greenhaven, Voidspire, teď my... a blíží se to k srdci království." Nothing in `useQuestStore`/`GameModule.tsx` enforces this ordering or cross-references — it's purely the `STORY` dialogue text itself accumulating a sentence per location, the cheapest possible way to make independent boss fights read as one unfolding season rather than unrelated errands.

**Solace closes the main storyline, and it's the one location in this chain that reuses the dungeon's multi-enemy shape instead of Emberfall's single-encounter one — on purpose, to make the finale feel heavier than the four story bosses before it, and it needed zero new mechanism to do that.** `NEPRATELE_PODLE_LOKACE.solace` is an array of two (Probuzený strážný, then První strážce as the boss — the spec's "The First Guardian"), so the existing "HP never restores between enemies at one location" rule that has applied to the dungeon since before this session automatically makes Solace the hardest fight in the game, no new state or flag required. `MapaSveta.tsx`'s long-standing "hlavní město je vyhrazené pro dějovou linku, ta zatím nevznikla" placeholder — reserved since the map rewrite, long before this phase existed — is superseded automatically the moment `SVETY_PODLE_LOKACE.solace` exists, because `jeExplorace` is checked before the capital-specific fallback in the sheet-text ternary; nothing about that branch order had to change to retire the placeholder now that the story it was reserved for finally shipped.

**Tuning Solace's two fights taught a real balance lesson, not just theming, and it's recorded as a comment on the boss entry rather than a number picked by feel and forgotten.** The first pass gave the First Guardian noticeably higher stats than every other boss ("it's the finale, it should hit harder") and the same kind of Playwright verification pass used to confirm every phase in this session couldn't clear it in six retries with a fresh, unlevelled level-1 character — every other Fáze-10 location was implicitly beatable from a brand-new character (that's what the identical verification pattern had already confirmed location after location), so a finale that wasn't wasn't a deliberate difficulty spike, it was an inconsistency the test caught. The fix wasn't to make the fight easy — it's still the second enemy in a no-heal-between sequence, so the *combination* stays the hardest fight in the game — it was to stop *also* stacking harder per-enemy numbers on top of that already-real structural difficulty. The boss's own stats now sit in the same range as the other four bosses; the two-fight, no-healing shape alone is what makes Solace the climax.

**Five relics now exist**, the fifth (Koruna prvního strážce, from Solace) deliberately breaking the "one archetype, one relic" pattern the first four established — it carries all three bonuses at once, and is the strongest single number in each category the equip slot has seen, because a season finale's reward should read as strictly better than what led up to it, not just differently specialized.

Still deliberately deferred, exactly as declined at the start of this session and reconfirmed here rather than forgotten: the remaining 25 side quests across all six locations. Each follows this same four-file recipe against whichever existing pin's region theme fits, added incrementally rather than fabricated wholesale in a single pass.

### Form Check (`src/miniapps/form-check/`)

A rep counter that watches the camera and counts squats via on-device pose detection — `@mediapipe/tasks-vision` (PoseLandmarker, WASM), no server ever sees the video. It's the template for "heavy on-device ML asset" if another miniapp needs one:

**The model and WASM runtime are self-hosted under `public/mediapipe/`, not fetched from Google's CDN**, so the app never depends on an external host staying up — same reasoning as "runs completely without the cloud" elsewhere in this file. That's ~28 MB (a 5.5 MB model, plus a SIMD WASM build and a no-SIMD fallback for older browsers) and it must **never** reach the install precache — nobody who skips this miniapp should download it. `vite.config.ts`'s `globIgnores` excludes `mediapipe/**`, and a `CacheFirst` `runtimeCaching` route fetches it lazily the first time Form Check actually opens, then serves it from the browser's cache offline after. Before assuming a library needs every file it ships, check what it actually requests over the network — the package here ships a third WASM variant (`vision_wasm_module_internal.*`) that `FilesetResolver` never asks for, confirmed by watching requests; it never went into the repo, saving another ~12 MB for nothing.

The camera + ML pipeline lives entirely outside React, same ownership shape as Social's `useAmbientScene.ts`: `usePoseEngine.ts` owns the `<video>`, the MediaStream, the `PoseLandmarker` instance and a `requestAnimationFrame` loop, and only pushes rep count / status / feedback into React state. Cleanup on unmount stops every media track and calls `.close()` on the landmarker — skip that and the camera keeps recording in the background after the user navigates away.

Rep-counting and posture math (`poseMath.ts`) are pure functions of landmark coordinates, deliberately kept free of the camera and of React, so they can be checked against made-up coordinates without a browser. The squat state machine needs a **gap between its two angle thresholds** (110°/160°, not one shared threshold) — without it, angle noise right at a single boundary counts a dozen reps a second instead of one. A rep counts on the way back *up*, not going down, so an unfinished squat never scores. Posture feedback ("narovnej záda") only fires during the down phase; everyone leans forward naturally at the top of a squat, and flagging that as wrong would just be noise.

Detection picks whichever side of the body (left/right) has higher landmark visibility each frame — a phone propped up for a side-on view of a squat always has one side partly self-occluded, and the model's guess for the hidden side is worse than for the visible one.

### Pomodoro (`src/miniapps/pomodoro/`)

**The running timer lives in the persisted Zustand store, not in React state, and its completion timer lives as a plain module-level variable, not a `useEffect`/ref.** Until this was flagged, `mode`/`timeLeft`/`isRunning` were transient hook state — leaving the miniapp (`AppModule.tsx` unmounts it, same as any other miniapp) threw the running block away entirely, and there was no way to know a block had finished unless the Pomodoro screen happened to still be open at that exact second. `usePomodoroStore` now persists `mode`/`isRunning`/`endsAt` (an absolute `Date.now()` timestamp, not a countdown — same reasoning as `registerSW.ts`'s `CHECK_INTERVAL` resume logic and the game hub's own `endsAtRef` pattern before this rewrite) alongside the settings/`completedSessions` it already tracked, and `completionTimer` (a `setTimeout` held in a module-scope `let`, armed by `start()`/`switchMode(..., autoStart)` and read by `usePomodoro()` only for display) survives the React component unmounting for exactly the same reason `core/utils/registerSW.ts`'s own module-level `registration` does: a plain JS variable's lifetime is the page's lifetime, not any one component's.

**This is a real behavior change from "don't persist the running timer, so you can't get credit for time the app was closed" to "you can, and that's fine" — because the mechanism is honest about it.** The old design's worry doesn't actually hold once completion is driven by an absolute `endsAt` rather than a ticking counter: whether the tab was open or not, the same real wall-clock time has to pass before `endsAt` is reached, so there's nothing to game. `onRehydrateStorage` handles the one case this couldn't otherwise catch — the block finished while the PWA process itself wasn't running at all (closed from multitasking, or a plain page reload), so the module's `completionTimer` never got to fire: on the next load, if `endsAt` has already passed, `complete()` runs immediately (once); if it hasn't, the timer is simply re-armed for what's left.

**The module-level JS timer's one honest limit — stated to the user up front before it was built — used to be "it's a JS timer, not a push notification," full stop.** It survives leaving Pomodoro for another screen in the app, or the phone's display sleeping briefly — anything that keeps the PWA's process alive in the background. It does **not** survive the PWA being force-closed from the OS app switcher or the device staying locked long enough for the browser to fully suspend the tab, because there was no server-side push infrastructure behind it — same class of thing `api/buddy-chat.ts` needed a real backend for its secret key for. That gap is now closed by a second, independent mechanism (below), built once this was explicitly asked for rather than left as an accepted limit forever.

**A second, entirely independent completion path — real Web Push via `core/utils/push.ts` + `api/pomodoro-push.ts` (Vercel Cron) — now covers exactly the case the module-level timer can't: the PWA fully closed or the tab suspended.** The two paths never replace each other, they race: whichever fires first is the one the user actually sees (the OS notification tray collapses a second, duplicate one anyway — both use `tag: 'pomodoro'`, the same collapsing behaviour this file documents for Social's chat notifications). `push.ts` is the client half — `zajistiPushPrihlaseni()` (subscribes the device via `PushManager.subscribe()` against a VAPID public key, upserted keyed on the subscription's own `endpoint` into `push_prihlaseni`) and `nahlasPomodoroCasovac(endsAt, rezim)` (upserts, keyed on `user_id`, into `pomodoro_casovace` — "this user's block ends at this instant"). Both tables are plain self-row RLS (`user_id = auth.uid()`), deliberately **not** `SECURITY DEFINER` functions — this feature has no cross-user privileged read from the client at all, so there was no reason to risk the exact PostgREST-default-EXECUTE mistake this file already documents catching twice elsewhere (`ma_pravo_na_tajny_chat`, `precti_verejny_profil`). `usePomodoro.ts`'s `start()`/`switchMode(..., autoStart)` call both `zajistiPushPrihlaseni()` and `nahlasPomodoroCasovac()` right after arming the module timer, using the exact same `endsAt`; `pause()`/`resetTimer()`/`complete()` all call `zrusPomodoroCasovac()` (deletes the row) — a block that finished, was paused, or was reset has nothing left for the server to notify about, so the row is removed the instant the client itself knows that, minimizing (not eliminating — a race between "client deletes" and "cron already read the row a second earlier" is possible and accepted, same `tag`-collapsing safety net as above) the chance of a redundant push for a block the user was already told about locally.

**`api/pomodoro-push.ts` is the third serverless function in the project, and its authorization shape is deliberately different from the other two.** `buddy-chat.ts` and `admin-ban.ts` both authorize a *specific signed-in user* (a session token, then a role check). This one has no user to check — Vercel Cron calls it on a schedule with no session, acting as a trusted background job, not on anyone's behalf — so authorization is a shared-secret header (`Authorization: Bearer <CRON_SECRET>`) instead, the same "server holds the only copy of the secret" idea as everywhere else in this file, just without a role lookup because there's no caller identity to look up a role *for*. It needs the service-role client for the same reason `admin-ban.ts` does: reading every user's due `pomodoro_casovace` row and every matching `push_prihlaseni` row across the whole table is exactly what self-row RLS is built to refuse. Each due row triggers a real `web-push` `sendNotification()` per subscribed device (a user could have more than one — phone and laptop both subscribed); a `404`/`410` response means the browser itself cancelled that subscription (app uninstalled, site data cleared), so the function deletes that `push_prihlaseni` row rather than retrying it forever. The `pomodoro_casovace` row is deleted after being processed either way — sent or not — so a transient failure doesn't retry every single minute until the row ages out some other way.

**The push handler itself (`public/push-sw.js`) is stitched into the generated service worker via `workbox.importScripts`, not written by hand into a custom `sw.js`.** `vite-plugin-pwa`'s `generateSW` strategy (this project's choice, documented under **PWA / offline** above) fully owns and regenerates `sw.js` — there's no file to hand-edit event listeners into. `importScripts` is Workbox's own escape hatch for exactly this: a separate, unbundled script the generated SW pulls in verbatim, the same mechanism `public/js/auto-update.js` uses for a different purpose (a plain page-level watchdog, not inside the SW at all — don't confuse the two). `push-sw.js` is excluded from precache in `globIgnores`, same reasoning as `auto-update.js` and `mediapipe/**`: it's infrastructure the SW loads itself, not a cacheable asset, and a stale precached copy could never self-correct. Clicking the resulting notification focuses an already-open tab if one exists, or opens a new one — the standard `clients.matchAll()`/`openWindow()` pattern, since a plain notification with no click handler just disappears with no way back into the app.

**Two operational facts have to be communicated to whoever deploys this, because nothing in the code itself can enforce or even detect them:** first, four new environment variables (`VITE_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `CRON_SECRET` — documented in `.env.example`) must be set in Vercel before any of this does anything; missing any of them makes `push.ts`'s functions silent no-ops and `api/pomodoro-push.ts` return a 500, never a crash, matching this codebase's "offline/misconfigured is normal, not an error" rule everywhere else cloud state is involved. Second, and unlike everything else self-hosted in this project: **Vercel's free Hobby plan runs Cron Jobs at most once a day, and this isn't a soft limit the cron silently misses — Vercel refuses the entire deployment outright if `vercel.json` declares a schedule the plan doesn't allow.** The first version of this feature shipped `"* * * * *"` (once a minute), which doesn't just fail to run as often as intended on Hobby — it blocks every single deployment of the whole app, not only this one endpoint, with a "Hobby accounts are limited to daily cron jobs" error at deploy time. That silently stalled two unrelated pushes (Pomodoro push's own follow-up work and, worse, the next feature after it) behind a production deployment that never actually went out, caught only when a manual "Create Deployment" surfaced the error in the UI. `vercel.json`'s schedule is `"0 6 * * *"` (once daily) for exactly this reason — Hobby-compatible so deploys never block on it. Upgrading to Pro and tightening the schedule back down is a one-line change whenever that trade is made; until then the module-level timer above still works exactly as it always did, so nothing breaks, but the "even after a hard close" guarantee this section describes only holds once a day, not every minute.

**`core/utils/notify.ts` is the app's first use of the Notification API** — Pomodoro was its first caller, `requestNotificationPermission()` called synchronously from inside `start()`, itself called synchronously from the Start button's click handler; both the permission prompt and `AudioContext` creation/`resume()` (the existing completion chime) need to run inside that same synchronous gesture chain or the browser silently refuses them. Showing the notification goes through `core/utils/registerSW.ts`'s now-exported `getServiceWorkerRegistration()` and `reg.showNotification(...)` rather than `new Notification(...)` directly — a plain constructor call throws in an installed Android PWA, so the service-worker path is the only one that reliably works there; the direct constructor is kept only as a fallback for contexts with no registration (e.g. dev without a SW). A failed or declined notification is never allowed to break completion itself — XP, the badge counter and the mode switch all happen regardless of whether the notification actually got shown. It started life as Pomodoro-only (`pomodoroNotify.ts`) and moved to `core/utils/` the moment Planer became a second caller (see **Planer** below) — same "promote to `core/` once a second feature needs it" rule this file already states for state/hooks.

### Planer (`src/miniapps/study-planner/` — id, hook and component are still `study-planner`/`useStudyPlanner`/`StudyPlanner`)

**Renamed from "Study Planner" to "Planer" — a display-text change only.** The id (`study-planner`), the store's persistence key (`schoolbuddy-study-planner-storage`), the hook/component/file names, and the `task` `ActivityKind`/`task_planner` badge id all stayed exactly as they were — renaming those too would mean a migration for zero user-visible benefit, the same reasoning that kept `ADMIN_TABS`' ids stable across the admin-panel menu rewrite. Every *displayed* string was found and renamed together in one pass — the app-grid title (`useAppStore.ts`), the miniapp's own header, the backup-list label (`core/utils/backup.ts`), and both places that mention it by name in the notification bell / rewards list (`ProfilNotifications.tsx`, `RewardModule.tsx`) — because a rename that only touches the obvious spot (the grid card) and misses the other four is worse than no rename: it leaves the app introducing itself under two different names in the same session.

**Reminders for due/overdue tasks are a second, independent use of `core/utils/notify.ts` — and unlike Pomodoro's, they can't be armed with a single precise `setTimeout`.** A task's `dueDate` is a calendar date with no time of day, so there's no exact instant to count down to; the right cadence is "check once, at most once per real day, whenever the app happens to be open" rather than "count down to a moment." `checkDueReminders()` (in `useStudyPlanner.ts`, same module-level-function shape as Pomodoro's `armTimer`) compares `tasks` against a persisted `lastReminderDate` and no-ops if that already equals today; `setupStudyPlannerReminders()` calls it once immediately and again on `visibilitychange`/`focus`/`online` (literally the same trigger set `registerSW.ts`'s `registerResumeTriggers` already uses for update checks) — cheap to over-call, since the date guard makes every call after the first same-day one a no-op.

**This reminder check has to work for a user who never opens Planer that session, which is why it's wired from `App.tsx`, not from `StudyPlanner.tsx`.** `useStudyPlanner.ts`'s store is already part of the main bundle regardless of whether Planer itself (the lazy-loaded `StudyPlanner.tsx`) is ever opened — `ProfilNotifications.tsx`'s existing `useStudyPlanner()` call (for the in-app "N nesplněných úkolů" bell item) pulls it in eagerly, since `ProfilModule`/`AppModule` aren't behind `React.lazy`. `setupStudyPlannerReminders()` is exported and called once from `App.tsx`'s startup `useEffect`, the same one-time-owner list as `setupPWAUpdates`/`startCloudSync`/`startRoleSync` — so a task's due-date reminder can fire even for someone who spent the whole session in the Hub or Social and never opened the miniapp itself.

**Notification permission is requested from `addTask()`, not from a dedicated button — creating a task is the clearest "I want this tracked" gesture this miniapp has**, the same reasoning as Pomodoro asking from its Start button rather than up front. The tradeoff, accepted rather than solved: a user who already has tasks from before this shipped and never adds another won't see the permission prompt until they do — not worth a dedicated "🔔 povolit upozornění" button just to close that gap.

### Vzhled aplikace (theming, `core/theme/`)

The Profil menu's "Vzhled aplikace" row was a `BRZY` placeholder since the very first pass at that menu; it's now a working feature — 5 color palettes, 3 free and 2 VIP-gated, picked from a visual grid in `SettingsModule.tsx` (`/nastaveni`), reachable both from there directly and from the Profil row, which now navigates instead of showing a toast.

**A "theme" here means one thing only: which values the app's own existing CSS custom properties hold — never a light-mode branch.** `global.css`'s `:root` already declares every color the whole app draws from by name (`--bg-base`, `--accent-cyan`, `--text-primary`, …) and hardcodes `color-scheme: dark`; no component anywhere reaches past those variables to a literal color. That's what makes re-theming a pure data problem: `core/theme/themes.ts`'s `Theme` interface has one field per existing CSS variable, `THEMES` holds five full sets of values (`nebula` — the *exact* pre-existing palette, so picking it is indistinguishable from theming never having shipped — plus `zapad`/`les` free, `zlata`/`polarni` VIP), and `applyTheme.ts`'s `aplikujVzhled()` just calls `element.style.setProperty()` once per variable. No page or component needed to change, and no second light-mode audit was needed either — every one of the five stays a dark palette, just a different hue family, because building a real light mode is separate, much larger scope nobody asked for here.

**A theme field's *name* doesn't promise its *hue* — `accentCyan` on the `zapad` (sunset) palette is actually amber, not cyan.** The names are inherited from the CSS variables they drive, which were never designed to be re-colored when they were first written; renaming them per-theme would have meant `themes.ts` and `global.css` disagreeing about what a variable is called. The name still identifies a *role* (this is the app's primary accent slot) even when a given theme fills that role with an unrelated color.

**VIP-gating reuses `cosmetics.premium`, the permission that already exists for exactly this** ("Prémiová kosmetika — motivy, avataři, rámečky" — CLAUDE.md's own `Permission` type had this described before any theme existed to gate). No new permission, no new role concept. `resolveActiveThemeId(themeId, maPremium)` is the same "evaluate on read, never trust what's stored" shape as `resolveActiveRoleId` — a VIP theme sitting in `useThemeStore` because the subscription later lapsed just silently resolves back to `nebula` rather than staying applied or throwing; nothing needs to actively downgrade the stored choice. That's also why `schoolbuddy-theme-storage` is `restorable: true` in `BACKUP_STORES`, unlike `schoolbuddy-role-storage`/`schoolbuddy-wallet-storage` right below it — a hand-edited backup claiming a VIP theme can't grant anything, because applying it re-checks the permission every time, the same reasoning that keeps a stored role assignment from being trusted at rest anywhere else in this codebase.

**The applied theme has to react to more than the picker screen — VIP can lapse while the user is in the Hub, not looking at `/nastaveni`.** `useAppliedTheme()` is a small reactive hook (not a one-shot initializer in the `setupPWAUpdates`/`startRoleSync`-style startup list) called from `App.tsx`'s own component body, subscribing to both `useThemeStore`'s `themeId` and `useHasPermission('cosmetics.premium')` — either changing re-runs `aplikujVzhled()`. It runs unconditionally, before the auth gate, so the chosen palette shows on the login screen too, not only once signed in. One accepted gap: because this is a pure client-side-React application step, not embedded inline in `index.html` before the bundle loads, there's a brief flash of the default `nebula` palette on cold load before the stored theme applies — closing that would mean duplicating `secureStorage`'s XOR de-obfuscation in a raw `<script>` tag the way `public/js/auto-update.js` does for its own narrower concern, which wasn't worth it for a cosmetic flash lasting a single paint.

**The picker grid is driven entirely by `VSECHNY_VZHLEDY`, no per-theme markup.** Each card's swatch is an inline gradient built from that theme's own `bgPanel`/`bgPanelRaised`/`borderStrong`, with three small dots colored from its `accentCyan`/`accentViolet`/`accentMagenta` — a real, if compact, preview of what picking it does, not a static icon. A locked VIP card (`cosmetics.premium` absent) stays visible and clickable rather than disabled or hidden — a user should be able to see what VIP unlocks — but dims to the same `opacity` treatment `settings-toggle-row--soon` already uses for "coming soon" rows, and clicking it shows "Tenhle vzhled je jen pro VIP." instead of applying anything; the active theme gets a highlighted border and a checkmark badge, reusing the `is-aktivni`/checkmark idiom this codebase already uses for selection state elsewhere (`PostavaKarta`, `TajnyChatPanel`'s tabs). Verified by an actual rendered screenshot of the grid (both with and without VIP) and by reading `getComputedStyle(document.documentElement)` after clicking a card to confirm the CSS variables genuinely changed, not just that a toast appeared — the kind of check unit tests and DOM-text assertions alone wouldn't catch for a visual feature. `resolveActiveThemeId` itself got a `tests/unit/theme.test.ts` (free-vs-VIP resolution, unknown-id fallback, the "exactly 3 free + 2 VIP, default isn't VIP-locked" catalogue shape) — the same pure-function-first pattern as `roleUtils.ts`/`leveling.ts`.

### Biometrické přihlášení (app lock, `core/utils/biometrics.ts`)

**"Biometrické přihlášení" in Nastavení's Zabezpečení card used to be a pure cosmetic no-op** — flagged in this session's own 100%-readiness audit alongside the equally-inert "Upozornění na přihlášení" toggle: `updateSecurity({ biometrics: zapnuto })` set a boolean nothing else in the codebase ever read. It's real now, built free — no server, no new library, no cost — via WebAuthn (`navigator.credentials`), a browser API every platform authenticator (Face ID, Touch ID, Android fingerprint, Windows Hello) already implements.

**This is an app lock over an already-authenticated session, not a second factor of the real login — and that distinction is load-bearing, not a footnote.** The actual account authentication is still, and only, Supabase email/password (`core/supabase/auth.ts`). A textbook WebAuthn flow verifies the assertion's signature against a server-stored public key and a server-issued challenge; there's no server here, so the challenge is generated locally in `biometrics.ts` and never verified against anything. That sounds like it should be worthless, but it isn't: a successful `navigator.credentials.get()` still cannot be forged from JS or by editing `localStorage` — the browser only returns success when the OS actually unlocked a hardware-bound private key via Face ID/fingerprint. What this buys is real (someone who picks up your unlocked phone can't get past the lock screen without your finger/face), it's just a client-side device lock, not a stronger login — the same "UI-only, the real boundary is elsewhere" honesty this file already applies to every client-side role check.

`zaregistrujBiometrii(jmeno)` creates the platform credential (`authenticatorSelection: { authenticatorAttachment: 'platform', userVerification: 'required' }`) and returns its `id`, stored as `ProfileSecurity.biometricCredentialId` (optional field — old profiles and profiles that never turned this on validate fine without it). `overBiometrii(credentialId)` re-asserts against that stored id later. Turning the toggle off cannot revoke the platform credential itself — WebAuthn exposes no delete API from JS — so it just forgets the stored id, which is all that's needed for the app to stop asking.

**`App.tsx` renders `BiometricLock` in place of the router when the lock is required, and the "required" decision is captured exactly once, in a `useRef`, at first render — not read live off the profile store on every render.** The first version read `profile.security.biometrics` directly in the render body, which meant turning the toggle *on* from inside a live session immediately swapped the entire app out from under the user mid-click — `App.tsx` re-renders on every store change, so the moment `updateSecurity` set `biometrics: true`, the very next render satisfied the lock condition and replaced `SettingsModule` with `BiometricLock` before the "Biometrie zapnuta ✓" toast even had a chance to show. Caught by the e2e spec itself (temporary, deleted after passing, same practice as every other Playwright verification in this file): the toast assertion failed because the DOM had already become the lock screen. The fix is `vyzadovaloZamekPriStartu = useRef(biometrics && credentialId).current` — computed once, frozen for the component's lifetime — so enabling biometrics mid-session takes effect on the *next* cold start, not the current one, matching what "Aplikace je uzamčená" actually implies (a start, not a live toggle).

**The lock screen always offers an unconditional escape hatch — "Nejde to? Vypnout zámek" — with no re-verification required to use it.** This has to exist for the exact scenario `profileValidation.ts`'s new optional field anticipates: `schoolbuddy-profile-storage` is `restorable: true` in `BACKUP_STORES`, so a backup made on one phone (with a `biometricCredentialId` bound to that phone's secure hardware) can be restored on a different device where the platform credential simply doesn't exist — `overBiometrii` would fail there forever, with no way back in. Letting the escape hatch disable the lock without proving anything isn't a hole: whoever can click a button running in that browser already has the same `secureStorage` access (XOR obfuscation, not encryption — see **State** above) any other client-side check in this file already treats as the honest boundary; the escape only prevents the app from bricking itself, it doesn't lower a real security bar that WebAuthn itself, absent a server, was never providing in the first place.

Verified with a temporary Playwright spec using Chromium's CDP `WebAuthn` domain (`WebAuthn.addVirtualAuthenticator`, `hasUserVerification: true`, `isUserVerified: true`) to simulate a real platform authenticator headlessly: toggled on (with the mid-session-lock bug caught and fixed in the process), reloaded to confirm the lock screen appears, unlocked via the simulated biometric assertion, reloaded again to confirm the escape hatch works and actually turns the setting off. One environment-specific wrinkle hit along the way, unrelated to app code: WebAuthn rejects an IP-literal `rp.id` ("invalid domain"), so the test had to navigate to `http://localhost:4173` rather than this config's usual `127.0.0.1` baseURL — a Playwright/Chromium quirk, not a change to how the app itself resolves its origin.

### Backup & restore

`core/utils/backup.ts` is the only way a user can get their data off a device — there is no backend. `BACKUP_STORES` is a hand-maintained catalogue of every persisted key; `collectFullBackup()` reads them into one versioned envelope (`format`/`version`/`createdAt`/`appVersion`/`data`) and `restoreFullBackup()` writes them back, recognising the pre-catalogue `{ apps: [...] }` format so older backups keep working. `backupValidation.ts` validates only the envelope — each store re-validates its own contents on rehydrate.

**Adding a miniapp with a persisted store means adding its key to `BACKUP_STORES`.** Miss it and the miniapp's data silently drops out of every backup. The auth store is deliberately excluded (restoring data shouldn't log anyone in or out). After a restore the app reloads, because the Zustand stores are already hydrated in memory and would not notice the new values on their own.

### File storage

File Manager keeps file *contents* in IndexedDB via `core/utils/fileStorage.ts` (`putFileBlob`/`getFileBlob`/`deleteFileBlob`/`listStoredFileIds`), not in `localStorage` — the 5 MB text-only limit there can't hold real files. Only the metadata (name, byte size, type, date) lives in the Zustand store. Blobs are **not** in the plain JSON backup (`collectFullBackup()`/`exportFullBackup()`) — base64-encoding real file bytes into one JSON string would make a backup with any meaningful amount of content unusable — but they *are* in the download the "Stáhnout zálohu" button actually offers.

**`core/utils/fileBackup.ts` wraps the same JSON envelope in a `.zip` instead of asking it to carry binary data itself, which is what actually closes this gap.** `exportFullBackupWithFiles()` (used by `Hub.tsx` in place of the plain `exportFullBackup()`) writes `backup.json` at the zip's root plus one entry per stored blob under `files/<id>` — no encoding overhead, a zip just concatenates bytes, so the practical size limit is now "however much file content a phone will comfortably download/upload," not "base64 inside one string." Importing detects `.zip` vs. a legacy `.json` by extension/MIME (`jeZipZaloha()`) and handles both — an older metadata-only backup still restores exactly as it always did, "content missing" message included. Restoring a `.zip` still calls the same `restoreFullBackup(envelope)` first (metadata into `localStorage`/`secureStorage`), *then* `restoreFilesFromZip()` writes the blobs into IndexedDB — deliberately in that order, and deliberately re-typing each blob from the just-restored File Manager metadata's own `FileItem.mime` rather than trusting whatever type (if any) survived the zip round-trip, since JSZip doesn't reliably preserve a `Blob`'s original `.type` through `generateAsync`/`loadAsync`.

**The in-app snapshot history (`backupHistory.ts`, the "Zálohy v aplikaci" list) deliberately stays metadata-only and wasn't touched.** Those snapshots exist to undo an accidental deletion *on the same device*, and file blobs live in a completely separate IndexedDB store that a metadata-only snapshot restore never touches — the content was never actually at risk from restoring one, only the entries pointing at it. The `.zip` export exists specifically for the cross-device case, where a fresh IndexedDB genuinely has nothing to point at. Verified with a real two-`BrowserContext` Playwright round trip (temporary spec, deleted after): upload a real file with known text content in one context, download the zip, close that context entirely (no shared state left anywhere), open a brand-new context, import the same zip file from disk, and confirm the restored file downloads back out byte-for-byte identical — not just that a metadata row with the right name reappeared.

### Responsive layout

The app is phone-first and must adapt to whatever screen it lands on — verified from 320x568 up to a 1024px tablet, portrait and landscape. Two global rules in `styles/global.css` do most of the work and should not be removed:

- `img, svg, video, canvas { max-width: 100% }` — media never outgrows its parent.
- `* { min-width: 0 }` — flex and grid items default to `min-width/min-height: auto`, which makes them refuse to shrink below their content. That default is what pushed the Hub's bottom bar off-screen: the mascot rendered 325px tall inside a 217px section and overflowed it.

Because `html, body, #root` are `overflow: hidden` and each page scrolls itself, **overflow is clipped rather than shown** — a broken layout silently loses content instead of producing a scrollbar. Never rely on the page scrollbar to reveal a sizing bug; check element rectangles against the viewport.

When a page has a fixed-height element sized from the viewport, drive it from the space the layout leaves (`height: 100%` on a `flex: 1` parent), not from its own intrinsic size. The Hub's `.hub-pet-img` is the reference: height comes from the section, width follows the aspect ratio, and `max-width` caps it on tall screens.

The Hub's bottom bar is `position: sticky; bottom: 0` with a gradient backdrop. Android often reports `env(safe-area-inset-bottom)` as 0 while the gesture bar still covers the bottom of the screen, so a bar that merely sits at the end of the content can end up underneath it.

Every full-height page pairs `height: 100vh` with `height: 100dvh` — keep both. `100vh` alone includes the area behind mobile browser UI and clips the bottom of the page.

### Path alias

`@/*` resolves to `src/*`, configured in **three places that must stay in sync**: `resolve.alias` in `vite.config.ts` (used at build time), `paths` in `tsconfig.json` (used by `npm run typecheck`), and `resolve.alias` in `vitest.config.ts` (used by `npm run test:unit`). Use `@/...` imports for anything outside a feature's own folder; use relative imports within a miniapp/page's own directory.

### Directory map

- `src/core/` — cross-app state (`store/`), roles (`role/`), app color themes (`theme/`), hooks, utils, types. Shared infrastructure only.
- `src/pages/` — route-level screens (`login/`, `hub/`, `app/`, `profil/`, `reward/`, `setting/`, `shop/`, `admin/`), each with its own `components/` subfolder and a single hand-written `.css` file (no CSS modules/CSS-in-JS).
- `src/game/` — the game hub behind `/hra`: character creation/roster, the world map, card combat (`combat/`), the in-game shop (`obchod/`), inventory/loot (`useInventarStore.ts`), equipment (`useVybaveniStore.ts`), 3D exploration (`explorace/`) and its data tables (`data/quests.ts`, `data/world.ts`, `data/story.ts`, `data/items.ts`, `data/equipment.ts`).
- `src/social/` — friends, chats and blocking behind `/social`; `api.ts` is the only Supabase caller.
- `src/buddy/` — the voice assistant launched from the Hub orb/mic; `api.ts` is the only caller of `api/buddy-chat.ts`.
- `src/core/support/` + `src/pages/support/` — support ticket threads behind `/podpora`; `core/support/api.ts` is the only Supabase caller, and `pages/support/SupportModule.tsx` serves both the user and admin view of the same screen.
- `src/miniapps/` — the individual study tools (see above).
- `src/features/miniapps/registry.ts` — the lazy-loading wiring between `pages/app` and `miniapps/`.
- `src/components/` — small app-wide shared components (`ErrorBoundary`, `NetworkStatusBanner`).
- `src/styles/global.css` — global styles, imported once from `main.tsx`.
- `api/` — server-side only, deployed by Vercel as serverless functions, never bundled by Vite. `buddy-chat.ts` (see **Buddy voice assistant**), `admin-ban.ts` (see **Admin panel**) and `pomodoro-push.ts` (see **Pomodoro**, Vercel Cron-triggered); typechecked by `npm run typecheck` via `tsconfig.json`'s `include`, same as `src/`.
- `tsconfig.json` — typecheck-only config for `npm run typecheck`; Vite never reads it for the build.
- `tests/` — see **Tests** above. `unit/` and `e2e/` (with its shared `helpers.ts`) are done; `components/` and `security/` are the planned remaining tiers.
- `vitest.config.ts` — Vitest's own config, separate from `vite.config.ts` (that one also carries the production build/PWA/version-manifest plugins, which the test run doesn't need).
- `playwright.config.ts` — `@playwright/test` config shared by `tests/e2e/` and (once built) `tests/security/`.
- `.github/workflows/ci.yml` — typecheck+unit and e2e as two independent jobs; see **Tests** above for why they're split and why the Supabase env vars are plain, not Secrets.
- `vercel.json` — cache headers for the update pipeline plus the SPA fallback rewrite (Vercel checks the filesystem before rewrites, so real files still win; `/api/` is explicitly excluded from that rewrite, or it would swallow every call to `buddy-chat.ts` before the function ever ran).
